# 越界、基线与候选选择：本地根因解析

2026-09-22。用户要求暂停新实验、采用先4构型调试再扩展4构型的思路，并授权本地根因追踪。服务器未连接，零新增物理步、零训练；冻结控制器与旧结果没有修改。本文补充和细化[v73覆盖报告](phase9_multiconfiguration_v73_report.md)，不是修复完成报告。

## 1. 越界检查的三种含义

当前代码分别检查物理状态限值、模型支持范围，以及命令/执行器约束。物理限值包括高度、速度、角速度、倾斜，接触/净空由真实适配器另行观测；它们是本实验设置的工程限值，不等于厂商硬件极限。命令还检查可控轴、幅值、变化率、PWM饱和和死区余量。

模型支持盒由每构型3条已验收fit轨迹生成：状态特征逐维最小/最大值加固定padding，命令范围加0.002。它只用于限制没有验证依据的外推，**不是准确性置信区间、不是控制不变集，也不是稳定性证明**。盒内不保证所有状态组合均有充分数据；盒外也不代表模型必定预测错。

检查预测轨迹可在发令前拒绝不合适候选；检查实际状态则发现模型误差、执行器迟滞或控制策略失效后的真实偏离。本实验触发后停止仿真并保留失败。真实机器人不能依靠“停止仿真”，仍需经过验证的恢复/安全控制。

uuv4本次触发的是模型姿态支持边界：目标俯仰约2.292°，该近纯俯仰轨迹的边界约2.531°，停止时约2.544°。没有发生接触或物理角速度超限。目标距数据边界的动态余量较小，但不能直接按失败点扩盒；若改变运行范围，应独立验证新范围的模型误差与可行控制。

## 2. baseline准确名称是PD反馈加物理补偿

控制对照每30Hz读当前状态：深度用位置误差P项和竖直速度D项；姿态用四元数/竖直方向误差P项和角速度D项。再按构型质量、惯量、浮力、恢复力矩计算目标力/力矩，通过原分配及PWM映射和统一限幅发令。

当前增益为深度P=1、D=2，姿态P=9、D=6；没有累计误差积分项，因此不是完整PID。它是传统控制思路，但比不带机械补偿的简单单回路PID更丰富。控制律未通过本轮数据训练；其支持范围与MPC一样受fit数据约束。

需要保留三个不同概念：

| 名称 | 当前含义 |
|---|---|
| 外部反馈baseline | 实际重新运行的PD+物理补偿对照，每周期更新需求 |
| MPC内部baseline | 从请求起点的状态计算一次目标力，生成未来受限命令序列，作为候选0 |
| persistence | 早期预测对照的状态保持假设，不是本轮闭环控制对照 |

外部反馈和MPC均使用同一构型机械信息、初始化、任务、seed与2秒长度。MPC内部优于候选0，不足以证明优于真实持续更新的反馈对照。

## 3. 根因追踪：从设计前提到实际失败

### R1 已确认：候选0的可行性被错误地当成所有成功返回的前提

现有[求解器](../koopman/bounded_mpc_v67.py)完成候选约束、PWM及预测筛查后，先判断候选0。如果它预测不可行，直接返回`baseline_prediction_infeasible`，不会选其他已判可行候选。

这条规则继承自09-03的“必须包含可行基准候选、比较同一目标改进”的设计。它适合基线已经可行时的优化比较，但没有提供“基线失效、其他候选可行”的恢复分支。因此是**可用性/恢复设计缺口，不只是if条件写反**。直接删除判断还会遇到基线cost为空、返回状态/收益语义及下游接纳合同问题。

uuv4真实证据：第180步捕获请求，第184步收到拒绝回复；候选3和6已经通过求解器的预测可行筛查，候选0不可行。整条回复仍无计划。该回复worker事件耗时43.754ms，小于100ms回复门；不是因超时拒绝。两条候选保持原8个60Hz网格前缀，原定激活为第196物理步；候选未执行，实际能否安全恢复尚未验证。

已建立最小复现，调用原v67求解函数，只用可控的合成预测结果隔离选择逻辑，不绕过选择函数：

| 输入情形 | 当前输出 |
|---|---|
| 基线可行 | 返回基线命令 |
| 基线不可行，候选3/6可行 | 返回无计划，丢弃两个可行候选 |
| 所有候选不可行 | 返回无计划 |

三种情形各重复两次，结果一致。执行`repro_selection.py --require-recovery`会在“存在可行替代应有恢复结果”的断言上明确退出1。这是已重现、尚未修复的缺陷信号，不把预期失败说成测试全绿。

### R2 已确认：旧计划保持可追溯，不代表未来保持可行

v54的设计是新回复被拒后保留旧活动计划；仍检查身份、真实命令历史、年龄和当前状态与原预测的偏差。但不会从最新实际状态重算整个剩余计划，也没有终端可行性保证。一个状态仍在允许偏差内，可以同时离支持边界很近。

uuv4实际时序如下，修正“旧MPC一直执行到最后才停止”的过度简化：

| 物理索引 | 实际事件 |
|---:|---|
| 184 | 新请求有两条预测可行候选，却因基线不可行返回无计划；继续旧MPC |
| 188、192 | 后续请求的7条已测试候选均不可行；继续旧MPC |
| 200 | 仍执行旧MPC末段 |
| 204 | 旧计划到期；转入反馈生成的命令，并作为新请求的承诺前缀执行 |
| 208 | 新请求仍无计划；继续反馈生成的前缀。实际俯仰力矩已为负，但俯仰角速度仍约+0.0301rad/s |
| 209 | 实际姿态越过支持边界，停止 |

这表明回退确实发生了，且已产生制动方向力矩；已有运动状态和执行器动态不能瞬间逆转。需要研究更早恢复及可行余量。不能据此证明“提前一周期回退就够了”，也不能把所有失败归于没有回退。

### R3 反例：uuv4_angled没有同样的可行候选窗口

其第184、188、192、208步收到的回复中，所有已测试候选均不可行。它最终第212步越界。因此R1修复有必要，但**不能保证修复uuv4_angled**。还需调查候选集合、承诺窗口、当前动量与支持范围匹配。有限候选全部失败不等于所有可能控制均不可行。

### R4 尚待验证：完整案例负收益的主因

long_body、uuv6等负收益与uuv4的候选拒绝不能直接等同。已有匹配命令短预测误差较小，支持优先检查目标归一化、内部基线与真实反馈差异、固定承诺窗口及有限候选。但尚未逐项消融，不能声称找到了这些构型变差的唯一根因。

## 4. 修复方向与4+4顺序

恢复后优先建立两类明确结果：正常优化结果与基线失效后的可行恢复结果。恢复可以不声称优于不存在的可行基线，但必须保留相同模型、状态/命令/PWM/前缀/时钟检查，并由执行端明确接纳；不是把`no_plan`改名为成功。

同时验证恢复是否及时、全部候选失败时如何处理，以及原计划还能安全执行多长时间。应补充“基线失败但其他候选可行”“全部候选失败”“恢复候选过期/实际状态偏离”“旧计划到期前已经需要制动”的反例，避免只覆盖成功优化和全失败路径。

建议第一组为base、uuv4、long_body、uuv6，分别覆盖已有正例、支持域失败、姿态负收益和深度负收益；第二组再覆盖asymmetric、uuv4_angled、uuv6_angled、heavy_moderate。这是4+4的建议具体名单，不将第二组称为未见构型独立测试。当前仅本地诊断，不自动恢复仿真或Goal；修复后的小范围真实验证才需要服务器。
