# 当前Koopman-MPC的计算效率与算法改进审核

2026-09-20。用户要求重新检查算法是否值得改进。本轮进行代码审核及本地冻结模型剖析，不连接服务器、不训练、不修改当前求解器或实时门。结论是：有明确的改进空间，优先改轨迹计算组织；GPU迁移和改换QP求解器均不应作为未经验证的直接替换。

这是Windows本地同一历史状态的重复诊断，既不是实时硬件测量，也不是独立控制episode；本地波动明显，不能用其绝对时间替代上轮服务器24.757ms往返结果，不能据6次记录估计可靠p99。直接调用没有IPC；保存的脚本从v62诊断派生，request标签沿用v62，但当前输出目录、入口SHA和测量模式独立明确。

## 第一优先级：不改模型和优化问题，减少重复工作

**A. 编译整段预测循环，而不仅是单步模型。** 当前[单步预测](../koopman/compiled_projected_v43.py)已有njit，但[时域循环](../koopman/command_batch_v45.py)仍在Python中逐控制区间、逐子步、逐候选处理，并为全部分支写入PWM、转速、加速度等详细数组。建议保持对外输入/完整结果合同，先做受控的内部数组循环编译；不先删诊断字段。数值内核复用原模型、float32执行器时钟和现有乘加顺序，保留故障分支隔离及分块deadline检查，外层独立进程仍执行100ms强制限时。

Numba官方建议依据实际数据profile优化，且支持将显式循环整体编译；这提供实现依据，不提供本项目加速倍数保证。保持fastmath关闭，避免为速度改变边界数值。[Numba 0.61.2说明](https://numba.readthedocs.io/en/0.61.2/user/performance-tips.html)。

**B. 同一次请求共享完全相同的前缀。** 当前20控制区间、每区间2子步，前8区间固定。此次9条候选中1条在死区筛查时拒绝，8条进入预测，原来共有320次“候选×物理子步”状态更新。若共享前16子步，再分成8条尾部，理论变成16＋8×24＝208次，减少35%的候选状态更新。原实现已批量调用预测器，因此这不等于模型调用次数减少35%，更不等于整个求解提速35%。必须同时共享正确的前缀执行器状态/float32时钟，维持各分支输出所有权、候选顺序和相同失败语义。不能跨请求复用旧状态。

**C. 合并同次请求的固定检查计算。** 原实现已缓存command→PWM/wrench映射，不能再把“首次缓存”当新贡献。仍可检查：同一静态目标在12个尾部区间中的重复复核、支持域和代价重复生成的姿态特征。建议共享不可变中间量，保留现时状态/支撑范围/死区/速率检查；不能缓存随状态变化的最终安全结论。

实施顺序：先比较A、B各自的真实收益，单项通过后再组合；C在剩余profile仍显示显著成本时处理。先覆盖8构型、不同历史长度、坏分支、饱和/死区与超时的结果等价，再用同一主机交错运行原版/新版，分别报告准备、求解、IPC和主控制耗时。既有全周期16.667ms与求解100ms门保留；不以降低候选数或缩短horizon作为第一步。

## 第二优先级：改善优化质量与规划延迟

[当前搜索](../koopman/bounded_mpc_v51.py)是基准序列加每个可控轴的正负扰动：4轴构型最多9条，3轴构型最多7条。这是有限候选的预测控制，没有连续QP/NLP的最优性保证。它易于限制运行时间，但不同控制轴需要联合调整时，单轴候选可能错过有用方向；这是代码结构局限，尚不是已证实的闭环失败原因。

值得比较的后续方案：将上一条仍有效计划按实际执行索引移位作为热启动候选，并在有限迭代/信赖域内作联合控制调整。旧计划必须重新绑定当前状态、模型、参考、执行历史和承诺前缀；不能无条件沿用。改变候选集合会改变算法结果，要单列算法试验，不能混在等价实现加速中。

8个承诺区间对应133.3ms，占20步预测时域的40%，剩余可优化尾部200ms。该前缀保证规划期间的已承诺执行一致性；它同时限制新方案最早生效时间。服务器单次24.757ms不能证明可以把前缀直接缩到2步；需要真实主链和求解尾部延迟、IPC及接收时限证据。等价提速后再评估缩短承诺窗口，观察响应速度、过期方案和回退比例，而不是先调低门。

## 第三优先级：是否改为Koopman-QP

经典Koopman-MPC的一项价值，是构造提升空间中的线性受控预测器，并使用线性MPC方法获得相近的优化复杂度。[Korda与Mezić原论文](https://arxiv.org/abs/1611.03537)。

当前被验证的预测分支每步读出并重新提升，另有四元数姿态更新、状态相关物理项、pre-TAM到PWM死区、执行器递推及非线性姿态代价。因此不能只把搜索函数替换为QP就宣称仍在求解相同问题，也不能直接继承该论文的速度结论。

如果A/B仍不足，或有限候选闭环质量明显不足，可研究在当前轨迹附近生成局部近似QP，warm-start求解后用原非线性模型及约束完整复核。它是新求解方法，需要近似误差/可行性与控制效果试验。另一条路线是重新取得真正线性提升预测的有效性证据；但旧完整提升分支已有失败，不应为了QP速度跳过预测验证。现阶段不重新训练或切换主模型。

## 决策

下一步优先A/B的等价CPU实现验证，保留C为profile驱动的后续；热启动与承诺前缀属于独立算法改进，QP属于更大的条件路线。当前证据支持“实现与计算组织值得改进”，不支持“GPU一定更快”“已达60Hz”或“Koopman控制收益已经成立”。本轮未修改求解器，没有新服务器任务。
