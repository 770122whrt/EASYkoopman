## 可直接定位的返回路径缺陷

`continuous_mpc_v76.py` 的 `solve()` 先调用求解器并取得 `solved` 和 `stats`，随后在 `Maximum_CpuTime_Exceeded` / `Maximum_WallTime_Exceeded` 分支立即返回。该分支位于读取 `solved['x']`、`solved['g']`、计算约束残差和精确验收之前。

因此本次日志中的 `no_plan` 表示**超时分支没有交付候选**，不表示最终迭代点一定不可行。原实现已经允许 `Maximum_Iterations_Exceeded` 下继续验收，但CPU超时返回没有走同一路径。v84外层仍正确保存并复核了已有计划，避免失去可行控制；这不等于NLP收敛问题已经修复。

原始两例缺少最后迭代的控制、约束值和KKT/线搜索过程，无法事后判断它是否已经改善目标或接近收敛。不能用外层保留计划的零违规值替代丢失候选的约束残差。

## 关于“为什么需要这么久”，目前能说到哪里

现有结构提供以下排查方向，但还没有因果证据确认其中某项主导了超时：

- 同时优化20个区间×4维控制，递推80个物理子步；状态、执行器和约束由单段展开的预测链计算。
- PWM分段死区、输入裁剪、绝对值推力，以及死区两侧互不连通的可行区，使问题非凸且部分表达分段；当前使用IPOPT的有限记忆Hessian近似。
- 目标包含米、弧度、速度和控制量，经不同权重及时间积分组合；约束也包含多个物理单位。代价约6.6e-4与严格优化容差值得检查，但**代价小本身不证明尺度不良**，也不能直接放松安全门或改目标权重。
- 未记录每步原始/对偶不可行度、线搜索次数、目标变化及函数/导数耗时，尚不能区分“每次迭代贵”与“需很多迭代才能收敛”。两种模型都超时只表明共同求解问题值得优先检查，不证明完全相同的根因。

## 最小下一步修复建议

完成当前冻结r2队列后，在新版本中修复返回流程，不改本轮模型、目标、约束或数据：

1. 将终止原因与候选质量分开记录。保留 `solver_timeout=true`、原始return_status及 `success=false`，不把超时改称收敛。
2. 求解器若正常返回且包含有限、维度正确的 `x/g/f`，即使超时也保存最后候选、原始目标与约束残差，然后执行原float32执行器和预测约束检查。必须同时计算控制决策上下界违规；不能只看g约束或相信求解器标签。
3. 仅从独立验收通过的候选和原有可行计划中按本模型的精确成本选择。超时候选比旧计划差或不可行时保留旧计划；超时候选更好且可行时可以标记“超时但获得可行改进”，不声称全局最优、收敛、实时性或闭环收益。
4. 外部硬杀进程、求解器抛异常或没有有限迭代点时，没有可恢复的候选；继续保留外层已有计划。不得伪造或插补候选。
5. 加入四类回归：超时且候选可行改善、超时且候选不可行、超时且没有候选、原计划不可行但候选可行。另保存有限长度的迭代/计时诊断，用原始与对偶残差、目标停滞和评估耗时决定是否需要无量纲化或其他求解改进。

这项修复首先恢复被提前返回丢弃的证据与可行控制。它不保证减少迭代数；应先看到同一起点、同预算下候选与收敛诊断，再讨论缩放、平滑近似或求解结构调整。当前两例尚不能比较P与Rc的新增控制收益。
