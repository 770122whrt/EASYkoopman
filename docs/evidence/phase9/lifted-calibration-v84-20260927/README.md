# LK来源数据正则校准：改善了pooled，但仍未达到控制准入

2026-09-27。沿用v84同一LK字典、机械描述、提升输入、线性传播和评价方法，只校准ridge。54次拟合，105.235秒，证据约31.1MiB；没有求解器或物理仿真。5项专项测试先红后绿并通过。原v84首轮负结果没有覆盖。

**结果：** pooled选择λ=1e−4，80步综合姿态RMS由首轮λ=.001的6.710mrad降至1.577mrad；但最坏窗口仍超门。8个LOCO构型全部未过门，72个80步窗口中32个未完成。因此不能送这个LK候选进入闭环，也不能以汇总平均掩盖失败。

## 选择过程没有看外部留出构型

`protocol.json`在任何拟合之前写入：固定grid `[1e-8,1e-6,1e-4,.001,.1]`，600秒/128MiB上限。每个外层折先排除目标构型，再把来源构型按名称排序的最后一个留作开发；其余来源拟合。每个候选均保存模型、开发评价及失败。最后按以下顺序选λ：

1. 80步开发窗口未完成数更少。
2. 完成窗口中最坏的 `z_RMSE / .002 + attitude_RMSE / .004` 更小。
3. 精确同分选较大的λ。

选择文件先落盘，随后在全部外层来源上重拟合，再评价外部构型。选择函数没有接收外部结果的参数。pooled也用同一来源开发规则，然后在全部八构型重新拟合/回代评价。它不是盲测。

选择最优不等于开发通过：**九折选择后的开发候选都没有达到原窗口准入门。** uuv6/uuv6_angled对应开发集上，五个λ均有9/9个80步窗口失败，λ=.1只是预定同分规则的结果，不是有效模型证据。其外层重拟合/预测仅作为这次有界离线诊断继续记录，不代表允许闭环。

## 为什么这仍是有价值的比较

**原来正则过强确实限制了pooled效果。** 改用只看来源数据选出的λ，综合80步姿态误差约下降76.5%。不能再用首轮两个较大λ的结果直接否定整个LK路线。另一方面，极小λ并不更好：pooled来源开发λ=1e−8有9/9失败，表明不能靠不断缩小正则解决问题。

**现在有更明确的传播方式诊断。** 对同一个pooled λ=1e−4算子，不改A/B，只在诊断分支每步解码后重新提升：

| 同算子比较，80步 | 综合姿态RMS mrad | 最大深度RMS mm | 最大姿态RMS mrad | 72窗口门 |
|---|---:|---:|---:|---|
| 保持提升状态线性传播 | 1.577 | 3.871 | 6.501 | 未过 |
| 每步重提升诊断 | 0.813 | 1.451 | 2.008 | 通过 |

这支持“当前字典的多步提升传播存在不一致/误差积累”是pooled退步的组成因素。重提升诊断不是用户要求的时域内线性传播，不能改名为LK成功；它也不能单独证明全部误差源，更不能改变外部构型失败。

匹配物理pooled80步综合姿态RMS约0.08394mrad，校准LK仍明显不如该强基线。有限加性LK对状态×输入交互的表达限制、490列设计面对少数机械配置的辨识条件，仍与此前[只读复核](../residual-attribution-v84-20260927/lifted-readonly-review.md)一致。本次只校准正则，没有加入新架构或据外部结果继续调参。

## 边界与复算

- 所有来源是历史fit轨迹；来源开发也已用于方法开发，不能声称新盲测泛化。
- 相同真实起点、相同已记录执行器加速度，时域内没有未来真实状态回灌；这是条件本体预测，不是完整控制链验证。
- 门阈值沿用v84，不因当前结果调整。所有候选、失败、选择和来源轨迹哈希均保存。
- 执行后核验`protocol.json`记录的校准脚本、LK实现、共同评价器哈希均未变化。
- 脚本：`workflows/calibrate_lifted_v84.py`；测试：`tests/test_lifted_calibration_v84.py`。命令：`.venv/Scripts/python.exe -B -m workflows.calibrate_lifted_v84`。已有输出目录会拒绝覆盖。
- 下一步不再盲目缩小λ。先结合Rc和控制链检查决定后续；任何字典/输入交互修改都应作为明确的新实验保留本轮结果。
