# 首周期归因与启动加速：v60 / v61

2026-09-20，31348服务器。用户继续授权修复、解释周期耗时并寻找计算加速。本轮完成剖析和启动准备修复：**最后一次无profiler的首周期为28.044ms，较原v59的544.064ms明显下降，但仍未通过16.667ms门。** 只测base、每次首周期即停止，MPC请求/激活仍为0；退出后的SIGSEGV仍未修复。

## 为什么原来这么慢

原544ms是完整仿真循环，包含CPU决策、GPU张量计算、物理推进、观察与安全审计，不是MPC求解时间。新的基线cProfile测得351.469ms，各函数累计时间中：

| 剖析对象 | 基线累计时间 | 含义 |
|---|---:|---|
| 两子步 `_compute_dynamics` | 271.724ms | 推进器、水动力及四元数等数学运算，主要热点 |
| `_get_rewards` | 32.795ms | 环境奖励计算也进入完整周期 |
| 两次SimulationContext.step | 6.026ms | 含PhysX推进；不是数百毫秒的主因 |
| 五次完整snapshot | 6.729ms | 含状态/telemetry/backend等读回 |
| 290次Tensor.cpu | 3.191ms | 同步读回频繁，但本次不是主要瓶颈 |

上表是不同层级的累计时间，部分相互包含，不能全部相加；GPU异步执行也使CPU归因不等于独立GPU核耗时。原544ms与新351ms来自不同启动，后者还含profiler开销，不能用二者差额声称一次修复收益。

目前证据支持**CUDA首次加载及数学函数首次执行准备开销**是主要来源：

1. 只将进程的 `CUDA_MODULE_LOADING` 改为 `EAGER`，带同样profiler的首周期由351.469ms降为160.201ms；`_compute_dynamics`由271.724ms降为112.999ms。启动时间随之增加。这是单次对照，尚非重复统计。
2. 对独立张量重复调用原有纯数学函数，观察到明显冷启动：四元数共轭第一次34.292ms、后续约0.05ms；姿态误差第二次201.270ms、之后约0.13ms；奖励第二次237.843ms、之后约0.18ms。只预热一次不足以覆盖本例的延迟准备。
3. 完成上述准备后，真实首周期测得28.044ms。该次关闭了cProfile，因此不能将160→28的全部下降精确归因于单一因素，但原始周期测量和纯函数多次调用均支持准备阶段有效。

[NVIDIA文档](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html)明确说明，延迟加载会把初始化放进首次执行窗口，建议在测量前预加载或预热。我们的实现保留原始冷启动失败，并单独记录准备开销，没有删掉首个控制周期。

## 已实现的加速及代价

- [纯数学准备](../workflows/runtime_prepare_v61.py)：仅对原四元数、水动力及奖励函数的私有张量副本作8轮调用，共56次。每次设备同步后计时，不调用env.step或执行器update。
- [加速诊断入口](../workflows/runtime_acceleration_v61.py)：在torch/CUDA导入前设置EAGER；reset后准备数学函数，再比较完整reset快照。只有前后完全一致才允许进入原控制循环。源与模型依赖只读复用冻结v59，输出在独立目录。
- 数学准备耗时0.5795秒，实际物理步数0；该成本单独报告。对应实际受控区间仍从原reset开始，16.667ms门不变。
- 准备前后完整reset快照一致；基线与加速后的两个物理子步逐一比较，state11、转速、PWM、推进器wrench、最终力和力矩差均为0（比较容差1e-6）。这仅覆盖本次base的两个子步，不代表全构型或任意轨迹等价。

新代码7项针对性测试加相关回归共**75 passed**。测试覆盖输入克隆、同步与异常传播、不接受环境对象作为纯函数输入、次数上限、状态改变时拒绝继续，以及旧形状/关闭与子步接口；并非全仓库测试。加速入口与本次服务器执行的源文件字节相同。

## 对“是否合理”和下一步的判断

首次运行包含数百毫秒准备成本是可解释的；把它当成稳定MPC每次求解耗时不合理。实时控制应明确设置准备完成边界，再从原始状态开始受控周期，同时报告准备成本。当前28ms仍不满足已有完整周期门，不能宣称60Hz通过，更不能从单个启动回退动作推断Koopman控制收益。

下一步按证据推进：

1. 对**准备后的路径**单独做分项计时，定位剩余约11.4ms差距，优先检查仍在周期中的首次计算及重复快照/后处理。只优化有测量依据的部分；安全检查不能直接删掉，缓存必须证明没有跨越状态或物理边界复用旧值。
2. 退出问题需要最小生命周期及原生栈取证，检查本任务新增接触view和trace引用的释放顺序；这是待验证假设，尚未直接改释放代码。取得原因后再修复。
3. 保留两种不同评价：算法控制效果按仿真时间评价；目标硬件实时能力评价完整传感—控制—执行链。GPU仿真器自身推进/研究审计的墙钟速度也需报告，但不能直接等同未来艇载MPC的计算耗时。当前冻结16.667ms门不改；如后续要让离线闭环效果与实时工程验证分开推进，应先明确新的实验口径。
4. 小批次单艇延迟与大批量采样吞吐不同。当前已经使用4090；先消除准备成本和数据往返、优化实测热点。并行多环境适合后续采样吞吐，不会自动缩短单条60Hz控制链；MPC尚无本次求解测量，不先盲目迁移GPU或增加进程。

当前是“已定位主要冷启动因素，并实现有真实改善的启动准备”，不是“整个性能问题已解决”。Koopman-UUV主线不变，匹配闭环、全构型、未见构型与Agent收益均未晋级。
