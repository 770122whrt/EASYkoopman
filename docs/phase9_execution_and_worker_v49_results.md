# Phase 9：执行确认与求解隔离已具备本地实现

2026-09-20。当前已补上一次性启动、唯一发令/确认历史，以及独立求解进程。新旧执行合同的相关测试通过；**尚未接通真实Isaac确认、MPC worker工厂和计划仲裁，也未完成完整控制周期计时或闭环验证。**

## 执行账本与历史重放

[v48执行账本](../koopman/execution_ledger_v48.py)将每条命令分成准备、提交执行和两个物理子步确认。准备与提交都不推进因果执行器状态；首次确认消费启动阶跃许可，第二次确认完成两子步hold。重复、乱序、错误身份或不确定执行会停止该episode，保留已经确认的部分。worker换代不清除在途命令或真实历史，不重发启动许可。

状态、reference、上一真实命令、历史摘要和执行器快照一起捕获。只有完整区间边界可以产生预测起点；最多保留256个区间供后续前缀核对。输入和对外数组独立持有，预测分支不能提交为真实执行。reset与ack仍依赖可信运行adapter，构造观察对象不等于证明真实复位/执行已经发生。

43项针对性合同包含在177项相关测试中通过。随后按[固定协议](evidence/phase9/execution-v48-replay-20260920/protocol.json)重放八构型旧fit PRBS各前32区间，保留[NO_GO结果](evidence/phase9/execution-v48-replay-20260920/result.json)：

| 构型 | 通过的旧命令区间 / 32 | 首个拒绝 |
|---|---:|---|
| base、long_body、heavy_moderate、uuv4、uuv4_angled | 各32 | 无 |
| asymmetric | 1 | 旧第二步变化率超过新0.01限制 |
| uuv6、uuv6_angled | 各0 | 旧首命令与本次准备的startup命令不一致 |

已通过161区间的原因果转速/时钟与上一命令核对通过，最大已测转速差0。这个门检验旧轨迹是否符合新发令规则，**不是新控制器闭环性能门**；没有更改旧轨迹或提高容差追求兼容。

[三例诊断](evidence/phase9/execution-v48-diagnosis-20260920/result.json)确认：uuv6两个首命令的主要差为+8.20e-7/−7.60e-7，原物理残差与PWM/死区都通过，但不能借另一条准备命令的身份放行。asymmetric旧第二步pitch/yaw变化0.01607/0.03674，确实超限，物理残差与PWM/死区本身通过。新控制器限速后的冷启动效果必须用后续实际试验判断。

## 确认开销与独立worker

旧确认接口计时为5.67–23.86ms，且未包含fallback/IPC，不能实时准入。[一次剖析](evidence/phase9/execution-v48-diagnosis-20260920/profile.txt)发现每区间两次原ControlKernel调用仍运行PID诊断，约4ms插桩时间，其中PID约3ms；这些诊断不决定直接pre-TAM的实际PWM。

[v49准备后的执行路径](../koopman/prepared_execution_v49.py)仅替换已确认命令的静态分配映射，复用已验证的v42直接分配。原两子步hold、float32时钟、执行器递推、事务式提交与快照代码保持。52项针对性测试通过，包括全部v48可观察合同和八构型变号命令与原递推逐边界对照。**去除该开销已有功能证据，新路径的完整周期性能尚未重测。**

[独立求解进程](../koopman/solver_worker_v49.py)采用spawn和单个未完成请求，默认请求/结果上限256/512KiB。低层不直接收发管道：独立I/O线程处理传输和结果解码，控制线程仅尝试访问单槽邮箱。这样避免“非阻塞检查发现半包后，真正读取仍等待”的问题。

默认父进程请求期限100ms，包含提交序列化、传输及结果解码；超时后该worker失去准入，晚到结果不再返回为候选。初始化/预热与关闭/重启只在生命周期入口执行，低层轮询不会等待进程退出。替换worker后必须同步执行账本的代次，同时保留实际历史。

14项真实spawn进程测试通过，覆盖正常返回、阻塞、超时、异常、崩溃、过大/不可序列化结果及初始化失败。故意阻塞5秒时，父进程100轮poll/第二请求拒绝在0.2秒测试上限内结束；这个较宽上限只证明隔离行为，不证明16.67ms的完整控制周期。

v49执行路径、worker及相邻接口的170项相关测试通过。[复核与已测源码](evidence/phase9/execution-v49-checks-20260920/review.json)记录各次原始退出码、来源与预算。实际测试worker使用可控fixture；尚未把正式MPC模型加载/预热接入该工厂。

## 下一步

接通真正的MPC worker与仲裁，逐项检查请求身份、真实命令前缀、计划年龄/激活位置及当前状态偏差。慢结果不能从旧第0步直接执行，回退改变已发前缀后必须使旧结果失效。还要为持续受限/无进展明确停止条件。

[源反例](evidence/phase9/deadzone-v49-probe-20260920/result.json)已确认：base零转速/零基准与8个±0.002单轴候选的原映射稳态推力全部为0，最大rawPWM为0.002000000095。该源检查不含模型预测或仿真，不证明所有运行点都会受困。下一版采用明确、因果的有界恢复命令序列作为基准；不能假设未来反馈已知，也不能把未发命令登记为真实历史。新增基准、承诺前缀和IPC开销必须重新参加完整求解/低层周期检查，不能沿用旧v45计时宣称通过。

这些接口齐备后，才能提出具体服务器冷启动/匹配闭环范围。Phase8.4冻结结果和关闭预算保持，MPC2-01..04仍开放。没有新拟合、正式test访问或服务器采样。

从v47完成之后新增已测153.934秒，源反例额外3.233秒后，当前本地阶段累计456.423/1200秒，剩余743.577秒；128MiB输出范围保持。所有本轮测试/诊断进程已结束，goal active，暂无需要用户处理的阻塞。
