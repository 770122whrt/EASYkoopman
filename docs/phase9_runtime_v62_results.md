# v62：退出修复、预热后开销与CPU求解实测

2026-09-20。继续用户授权的修复与GPU/实艇部署分析，未训练或改动冻结模型。本轮已结束，无后台任务。

**结果：退出段错误在3次base真实短运行中均未复现；完整仿真周期仍未通过16.667ms门。禁用CUDA后，冻结Koopman-MPC在服务器CPU完成1次请求，往返24.757ms，满足该次100ms求解门。它不证明艇载60Hz，也不证明闭环收益。**

## 修复和对照

安装版本的SimulationApp.close会卸载原生插件。旧trace仍持有contact getter、环境和绑定方法，collector也保留环境别名，导致原生依赖可能活到插件卸载之后。新[lifecycle helper](../workflows/runtime_lifecycle_v62.py)先释放本任务持有的观察器/环境引用，再关闭SimulationApp；不用强制退出伪造成功。

4项回归测试验证释放顺序、未退出观察器不能静默释放、关闭错误保留，以及worker未完全join不能报关闭成功。服务器3次均保存最终报告、三个关闭步骤完成且错误列表为空；父进程观测到退出码1，准确表达周期门失败，替代旧SIGSEGV(-11)。这支持生命周期修复，但没有取得C/C++故障栈，不能声称排除了所有原生退出缺陷。

| 尝试 | 内容 | 完整周期 | 真实结果 |
|---|---|---:|---|
| 01 | 原数学预热＋生命周期修复＋cProfile | 32.112ms | 超时停止，native 1，无段错误 |
| 02 | 同上，关闭cProfile | 29.382ms | 超时停止，native 1，无段错误 |
| 03 | 在02上批量读取GPU快照 | 36.831ms | 超时停止，native 1，无段错误；不采用该加速候选 |
| 04 | CUDA不可见，仅CPU上一条历史fit原点的冻结MPC请求 | 不启动仿真 | 往返24.757ms，返回selected，native 0 |

前三次各完成1个启动回退区间、2个实际物理子步，MPC请求/激活仍为0。第4次是独立离线求解，不能计为真实闭环的MPC激活。

新[诊断入口](../workflows/runtime_acceleration_v62.py)与服务器attempt02源字节相同，保留原预热、检查和失败门。它仍不是正式准入发布包。批量快照候选仅保留在[独立模块](../workflows/runtime_snapshot_v62.py)和attempt03证据中，没有切换为默认路径。

## 为什么GPU没有直接解决剩余耗时

准备后的cProfile定位如下，累计时间存在嵌套，不能相加：动力学计算6.305ms，5次完整快照6.188ms，模拟器推进3.256ms，coordinator.step 3.743ms；290次Tensor.cpu累计2.965ms，奖励计算仅0.697ms。coordinator此时执行的是启动回退，不能把3.743ms称为MPC求解时间。

批量快照保留全部字段、顺序和dtype，在每次getter后立刻clone以防后端复用缓存，再按设备/dtype合并传输；没有跨物理边界缓存。它在CPU夹具及实际reset与旧快照相同，前三次相同两个子步的before/command完整快照、物理后状态、backend及contact对照最大差0（容差1e-6）。但无profiler首周期比原路径慢7.449ms，因此不采用。仅从单次对照不能估计稳定平均回归幅度；至少没有得到加速证据。克隆、打包与调度本身也有成本，“少调用cpu”不自动等于总耗时更短。

当前约29ms对既定60Hz全周期要求仍不合格。它包含Isaac物理推进、研究快照及各项核验，不是纯控制器耗时；也不能因为它不合格就宣布Koopman预测或控制方法无效。

## 实艇是否需要GPU

当前`portable_model_factory`使用NumPy/Numba CPU预测内核和独立CPU求解进程，没有将MPC迁移到CUDA。此次[CPU诊断入口](../workflows/runtime_cpu_check_v62.py)在导入计算库前设置`CUDA_VISIBLE_DEVICES=-1`，确认`torch.cuda.is_available()==false`，复用原冻结模型与一个base fit原点，只提交一次请求，不拟合、不启动Isaac、不读取正式test。

- worker准备5.521秒，位于请求计时之前；不是每次求解成本。
- 请求提交至父进程收到解码结果24.757ms；worker记录24.743ms；结果selected，原100ms求解门不变。
- 24.757ms仍大于16.667ms，所以这也不支持“每个60Hz周期同步重求一个MPC”。当前设计是独立worker异步规划，主控制链逐区间执行和验证可用计划/回退；两个截止时间分开验收。
- 实艇不运行Isaac物理引擎及奖励函数，需测实际传感/估计→控制决策→分配→执行器通信的完整路径。服务器单原点CPU结果不能替代目标艇载硬件上的长序列、尾部延迟与最坏情况验证。

因此现阶段CPU是可行的实现起点，GPU不是当前Koopman-MPC的必需依赖。是否给实艇配GPU应依据目标硬件测量和未来视觉/深度网络负载决定；目前没有证据要求为了这次问题采购GPU。

## 下一步与证据边界

1. 保留已验证的启动准备和生命周期修复，停止推进批量快照候选。继续优化时先剖析具体同步/重复读取及固定安全计算；不能删除安全门或跳过失败首周期来获得通过。
2. 下一项测量需要分别报告主控制路径、异步求解、物理推进和研究审计成本。优先消除同一边界的重复计算，任何缓存必须证明失效边界正确。当前完整16.667ms门保持NO_GO。
3. 若研究审计/仿真推进继续阻挡效果验证，应单独制定“按仿真时间评价控制效果”和“目标硬件实时性”的协议，明示两者证据边界；不能事后把当前失败改成通过。本轮不执行新闭环协议。
4. 只有实际MPC闭环激活后才能做Koopman-MPC、Legacy、仅反馈回退及同优化器物理模型的匹配收益比较。未见构型、适应、Agent收益继续后置。
