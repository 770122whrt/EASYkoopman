## uuv4失败说明了什么

反馈基线完成60控制区间/240物理步。MPC在1.741667秒停止：重力方向的机体x分量从−0.0441553356变为−0.0443947962，训练支持下界为−0.0441609455；俯仰角约0.0444094rad，目标0.04rad。没有接触或物理安全角速度超限。

求解器在物理索引184、188、192、208已经返回`baseline_prediction_infeasible`，均在约6.8–7.9ms内返回；当前仲裁仍按原规则执行既有计划或承诺前缀，最终越界。**这一失败首先暴露了保持可行性与回退控制的不足，不能简单归咎于计算慢或Koopman一步预测失准。** 用最后一步真实状态和真实作用力做事后一步预测，也预测越界，重力方向分量与实际只差约7.16e−7；这是教师强制诊断，不是在线预测或多步精度证明。

在共同209步前缀上，MPC姿态RMSE为0.0184982rad，反馈为0.0194875rad；但深度RMSE分别为0.00350761m和0.00171629m，综合误差几乎相同。此前缀比较仅用于解释误差交换，**不覆盖剩余31步，不用于通过收益门**。

v72在原Linux数值环境严格重放了全部209步控制/执行器历史、52个完整区间、最后1个子步、11次MPC接管和4条终止事件。正例通过；worker清理、命令、回执、仲裁、接管次数、终止原因、早期状态、接触记录共8项篡改均被拒绝。原v71运行失败和其旧分析器的失败记录原样保留；新增复核只把失败分类为NO_GO，没有把原退出1改成成功。

## 工程问题与修复证据

1. 原预热遗漏了配置分配器的GPU pinv/WLS，首次调用造成193.533ms控制启动和127.5MiB运行段RSS增长。私有张量预热原分配函数后，先前实测首周期52.416ms、RSS增长5.656MiB，reset不变、原4步状态不变。
2. gdb捕获退出崩溃链：Python终结时释放保留的异常/栈帧，继而释放`EasyUUVEnv → RigidObject → SimulationView`，在PhysX tensor析构中SIGSEGV。`DirectRLEnv.close()`删除scene，却未移除EasyUUV自己的`_robot`引用。v70在环境关闭完成后释放该别名，弱引用确认机器人已销毁，然后关闭SimulationApp。具体缓存异常的产生点没有进一步追踪；修复不依赖忽略该异常或强制进程退出。
3. v70真实uuv4反馈原生退出0，服务器和本地重放通过；修复前后全部240步状态及60条命令最大差均为0。后续MPC支持域失败也正常返回1，没有再次段错误。其他构型退出情况仍要逐例验收。
4. Windows/Linux float32分配产生约1.12e−8的PWM差，放大为约2.10e−7残差差。v70先独立核对命令→记录PWM，再由记录PWM重放作用力和残差，原1e−7容差及物理布尔门不变。uuv4残差重放误差为0。
5. MPC内部仲裁的执行器状态比较使用1e−12精度，Windows重新计算的float32分配会产生约9.09e−7转速差。因此严格仲裁在原Linux数值环境执行，本地另外完成物理/输入前缀检查；本地部分重放结果明确禁止单独授权隔离。不能称所有Windows仲裁检查均通过。

完整周期仍约50ms，超过30Hz的33.333ms；预热与退出修复没有解决实时资格，也没有改变模型或控制参数。
