# 八构型覆盖报告：局部收益成立，统一控制收益尚未成立

2026-09-21。用户批准v73资源修订后，31348服务器完成15次新增物理启动，零训练、零重拟合。最后的heavy_moderate反馈触发持续无进展，队列按原规则全局停止，没有追加仿真。八种构型均已尝试；本轮有界覆盖报告交付，**Phase 9仍开放，Phase 8.4保持关闭**。

## 1. Koopman-MPC现在有没有收益

**base俯仰短任务有局部跟踪收益；新增构型没有出现新的有效收益案例。** 不能据此宣称统一策略在多构型上优于反馈，也不能把这些结果称为Koopman独特表示收益。

反馈对照是配置感知的物理反馈控制，不是早期预测实验中的persistence。本轮冻结同一pooled预测模型、控制权重、候选搜索、支持范围和30Hz执行规则；构型质量、惯量、浮力、阻力、执行器分配及可控轴作为显式机械信息输入。是已知构型上的同规则测试，不是未见构型LOCO。

每条完整轨迹为2秒、60个30Hz控制区间、240个120Hz物理步，seed19500。俯仰目标0.04rad并保持z=5.5m；深度目标z=5.48m并保持水平。百分比为`(反馈综合误差−MPC综合误差)/反馈综合误差`，正值更好。综合误差是深度误差平方除以0.02²，加姿态角误差平方除以0.04²后取均值。

## 2. 跟踪改善与控制代价必须一起看

俯仰任务的MPC/反馈比值如下。力/力矩平方积分是控制作用量代理，不是电池能耗或电机功率测量。

| 构型 | 命令总变化量比 | 力平方积分比 | 力矩平方积分比 |
|---|---:|---:|---:|
| base | 1.821 | 0.810 | 3.871 |
| long_body | 2.244 | 0.528 | 11.952 |
| uuv6 | 6.022 | 0.968 | 5.209 |
| uuv6_angled | 5.575 | 0.968 | 5.072 |

base的改善伴随更多力矩作用，尚不能称整体工程效益已成立。long_body付出更大力矩代价，姿态RMSE反而从0.018200升到0.019204rad。uuv6俯仰深度RMSE从1.490增至3.823mm；uuv6_angled从1.293增至3.737mm，是综合指标下降的重要组成部分。

深度任务中，uuv6/uuv6_angled命令变化量均约为反馈的0.70倍，但深度跟踪变差；long_body深度仅改善约0.017mm，力平方积分约1.947倍。纯深度的力矩基线约1e−12至1e−15，相关比值不宜作有意义的节能结论。原始绝对值保留于[机器汇总](evidence/phase9/remaining-coverage-v73-20260921/coverage-summary.json)。

## 3. 失败发生在哪里

### 已确认：uuv4系列是计划可行性问题，不能用截断轨迹报告成功

uuv4在1.741667秒、uuv4_angled在1.766667秒越过姿态支持边界；两者均实际接管11次，反馈臂均完整通过。

uuv4_angled最后一步机体系竖直方向x分量从−0.0447061022变为−0.0450652780，低于下界−0.0449339200。物理索引184、188、192、208的求解均返回`baseline_prediction_infeasible`，耗时7.875–9.008ms；现有仲裁规则仍保留原活动计划/承诺前缀，最终实际状态越界。服务器完整重放了212步历史、仲裁与停止事件，本地另行重放物理/命令前缀。

这确认了当前执行机制没有保证后续持续可行。它不等于找到了安全可用的替代控制，也不证明只要缩短前缀就能修复。不能放宽支持盒、忽略失败、把停止前改善当作通过。

### 已确认：heavy_moderate尚未进入MPC，反馈限幅发生通道耦合

真实停止发生在80物理步/0.666667秒之后、下一条命令发出之前。20次反馈发令、0次MPC请求、0次接管；原生退出1，清理完成，无段错误。

末段深度命令为0.554189622，支持上界0.554189648；静态反馈希望达到0.573384821，超出支持范围。四个通道共用一个插值系数，深度通道把系数压到约1.34e−6，连俯仰通道也只能改变约3.82e−8，低于1e−7的无进展阈值。进展保护独立重算在同一边界停止；80步状态仍在支持范围、接触与物理筛查通过。因此**不是本次实际支持域越界，也不是Koopman预测失败**。

在最后一条已记录状态上，仅用于诊断的逐轴裁剪仍满足命令约束，俯仰加速度残差由约1.278降至0.385rad/s²；深度残差仍约−0.287m/s²。这说明确有可利用的俯仰调整空间，但不能消除深度饱和，不能凭这一个静态计算宣布闭环修复。

此失败不在已批准的“支持域NO_GO可隔离”范围内，故保留`global_stop`，heavy余下3臂未运行。原监督器的嵌套构型字段仍写`running`、`not_run=[]`，是异常分支未收尾的旧元数据；顶层global_stop、原生退出、进程审计和本报告明确其已停止。冻结原文件未改写，机器汇总独立列出真正未运行单元。

### asymmetric：冷启动问题仍在，原离线候选未修好

反馈第10物理步滚转越界，MPC还未请求。零转速启动的力矩建立过程与统一限幅共同构成候选机制；既有逐轴/水平保持/增阻尼离线尝试并未可靠修复，不能迁移heavy的单状态诊断作为它的成功证据。原fit包含冷启动，不能称训练数据完全没有初始化过程。详见[启动取证](phase9_startup_v68_findings.md)。

## 4. 当前证据更支持先修控制设计，而非先扩大模型

新增[在线预测片段诊断](evidence/phase9/remaining-coverage-v73-20260921/matched-forecast-diagnostics.json)只比较原worker已输出预测，且逐步确认计划命令与真实命令完全匹配，首次改命令即截断。它不重拟合、不用未来观测替代预测起点。

在约0.267秒的匹配片段上，俯仰案例深度预测RMSE约0.5–1.2微米、姿态约7.8–8.5e−5rad；这些量明显小于真实闭环的毫米级深度误差和约0.018rad姿态跟踪误差。片段有重叠、来自已知构型和已接受计划，不能外推到未执行候选、域外、长时域或未见构型。结论是：**在已检查片段中，不能用明显的短期预测失准解释全部负收益；优先控制设计排查有依据。** 这仍不是完整因果消融结论。

已从代码确认的设计差异，及其尚待验证的影响：

1. 优化代价使用原始m²/rad²、速度惩罚、命令努力和终端项；报告采用0.02m/0.04rad归一化跟踪指标。两者不是同一个目标，较低优化代价不自动等于更好报告指标。
2. 内部恢复基线在请求起点计算一次目标力，再沿未来生成限幅命令；真实反馈对照每30Hz重新计算状态反馈。因此“优于内部基线”不等于“优于真实反馈对照”。
3. 20个60Hz预测网格仅约0.333秒，其中8格/0.133秒为已承诺前缀，自由未来部分约0.2秒。完整MPC臂通常14次新计划接管、45个承诺前缀区间、1次回退；不能只把标记`mpc`的14个区间当作全部MPC影响。
4. 候选是基线加单轴正负扰动，最多9条；没有多轴联合优化或连续QP最优性的证据。新计划不可行时延续旧计划，也没有递归可行性保证。

上述性质来自[目标函数](../koopman/control_objective_v44.py)、[恢复基线](../koopman/inexact_tracking_v66.py)、[30Hz时序](../koopman/rate30_v67.py)、[候选搜索](../koopman/bounded_mpc_v67.py)和[计划延续](../koopman/plan_continuity_v54.py)。影响大小需要逐项消融，不能将四项合并修改后宣称发现唯一原因。

## 5. 工程、数值和实时性结论

预热补齐和原生生命周期修复继续有效：新增13个完整案例原生退出0；两个负结果正常返回1，均无残留进程。2965项原依赖、IsaacLab补丁、原冻结release及已部署manifest文件哈希均未变。

v73原始结果180个文件的服务器/本地SHA256一致。13个完整案例在Linux通过原完整物理、仲裁和残差验收；Windows独立重算物理/输入/指标也通过。9个案例通过Windows严格仲裁；uuv6和uuv6_angled的4个MPC案例受float32分配与内部1e−12比较影响，未声称Windows严格仲裁通过，完整仲裁以原Linux记录为证。

另有uuv6深度反馈两次float32点积的末位差1.1920929e−7N，物理判定未变。新增离线审计器以相同float32乘数的float64和为参考，按累加项数推导舍入误差界；同时核对记录力与残差的一致性、重算物理布尔门及原命令绑定。没有修改控制器、支持盒或物理容差。针对篡改PWM、力、残差及布尔结论的检查通过。所有跨平台限制明确保留。

本轮相关本地检查为**52 passed、4 skipped**；4项是已知平台相关严格MPC重放限制，不称全平台通过。原uuv4严格Linux重放及8项反例检查仍保留。heavy新增诊断只重算物理/命令、反馈记录与进展保护，不冒充完整仲裁摘要重放，也不授权隔离。

**30Hz仍未获得实际墙钟资格。** 新增完整案例稳态周期中位数约44.8–52.2ms，稳态最大值最高65.2ms；每条59个非首周期均超过33.333ms。首周期豁免不能解决这些稳态超时。当前结论来自仿真效果模式；求解耗时和包含物理/读回/审计的完整周期必须分开。GPU已用于仿真，增加GPU不能直接修复上述控制逻辑问题。

## 7. 下一步按什么顺序走

**保留Koopman-UUV目标，Phase9先修安全和控制效果；暂不进入自适应/Agent。** 本轮没有证明“Koopman无效”，但已经否定“当前统一控制实现已具有跨构型普遍优势”。

1. **先做本地失败修复设计。** heavy检查支持盒与反馈可达需求、共同插值锁住其他轴的问题；uuv4系列检查新计划失败后的原计划余量、回退可行性与承诺前缀。保持初始状态、支持范围和原门，先用记录状态复现与反例检验。若安全启动确需改变初态/预稳定阶段或补数据，明确形成新实验边界，不追改本轮。
2. **做最小控制消融。** 在同一模型下分别检查目标归一化、内部比较基线、承诺窗口和候选集合，每次只改变一项。先解释long_body俯仰、uuv6深度两个负结果，并用base俯仰做回归检查。离线静态改进或预测改进不能代替真实闭环；本轮轨迹一旦用于改进就作为开发材料，后续收益须用预先冻结的新初态/seed/任务验证。
3. **效果成立后再做收益归因。** 在相同控制目标、约束、时序、调参额度和评估预算下比较名义参数模型、辨识参数模型及当前学习预测模型，分离参数收益与表示收益；不能把投影动力学/已知运动学的效果全部归为完整Koopman算子。再增加构型与更长任务；未见构型、自适应和Agent贡献分别验证。

当前没有新训练或新控制版本在服务器上运行。新物理修复实验应先有具体实现、反例验证和有界配对协议，再依据已有授权范围执行；若改变停止范围、初始化合同或明确资源上限，则在运行前说明所需决定。不要仅为填满覆盖表而把heavy改标为可隔离NO_GO。
