# Phase 5.3: Cross-Combination PPO Health Screening - Specification

## Goal

Run a bounded cross-combination screening matrix over the Phase 5.2 reward, adapter and MPC single-axis signals, then select the best overall parameter combination for the next tuning/evaluation phase.

This phase answers:

```text
Do any Phase 5.2 single-axis improvements become better when combined, especially
`reward_v1_only + adapter_scale_soft_v1`, and which combination gives the best
multi-metric tradeoff across PWM saturation, fallback, action clipping and RMSE?
```

## Background

Phase 5.2 ran a one-factor ablation on `agentic-AUV`. The best balanced candidate was `reward_v1_only`:

| Profile | Fallback | PWM saturation | Action clip | Latency mean ms | Depth RMSE | Attitude RMSE |
|---|---:|---:|---:|---:|---:|---:|
| `baseline_rerun` | 0.2333 | 0.2293 | 0.0517 | 11.8990 | 0.8564 | 0.8135 |
| `reward_v1_only` | 0.1248 | 0.3379 | 0.1393 | 11.7225 | 0.9360 | 0.7434 |
| `adapter_soft_v1_only` | 0.1114 | 0.3963 | 0.1088 | 11.7759 | 1.0074 | 0.7449 |
| `mpc_health_v1_only` | 0.1524 | 0.3731 | 0.4952 | 11.7458 | 2.0573 | 0.7004 |

Interpretation:

```text
reward_v1_only improved fallback, but worsened PWM saturation.
reward_v1_only also increased action clip and depth RMSE versus baseline_rerun.
adapter_soft_v1_only improved fallback slightly more, but worsened saturation and depth more.
mpc_health_v1_only caused too much clip/depth regression.
```

Therefore Phase 5.3 should not jump to LLM or broad PPO hyperparameter search. The next clean step is to run a small, explicit cross-combination screening matrix. The result of that screen decides which parameter family enters the next tuning/evaluation phase.

Phase 5.3 also makes explicit that saturation is not the only target. The chosen combination should push down as many health metrics as possible: PWM saturation, fallback, action clipping, depth RMSE and attitude RMSE.

## Algorithm Contract

The control chain remains fixed:

```text
obs_9d
  -> RSL-RL PPO policy
  -> action_4d
  -> heuristic_reference_delta_v0
  -> koopman_reference_5d
  -> direct_state Koopman+MPC
  -> pwm_8d
  -> Isaac EasyUUV physics
```

Phase 5.3 may only change versioned reward, adapter and MPC profile metadata around this chain:

```text
cross-combination profiles:
  reward_profile x adapter_profile x mpc_profile

training ladder:
  sentinel -> candidate -> optional extended candidate

selection gate:
  compare all combinations against Phase 5.2 reward_v1_only and baseline_rerun
```

Phase 5.3 must not replace RSL-RL PPO, change the PPO observation/action dimensions, let PPO output PWM, change Koopman model class, promote `paper_lifted_edmd`, or introduce LLM control.

## Cross-Evaluation Status

Phase 5.2 did not run a combined cross-evaluation. It ran one-factor ablation:

```text
baseline_rerun
reward_v1_only
adapter_soft_v1_only
mpc_health_v1_only
```

That was the right first test because it preserved attribution: each result can be traced to one changed subsystem. But Phase 5.2 now gives enough evidence to run the specific cross-combinations that might be complementary.

Phase 5.3 therefore uses this two-stage structure:

```text
Stage A:
  cross-combination screening over Phase 5.2 reward/adapter/MPC profiles

Stage B:
  take the best Stage A combination into the next parameter tuning/evaluation phase
```

Initial Stage A cross candidates:

| Cross profile | Reward variant | Adapter profile | MPC profile | Purpose |
|---|---|---|---|---|
| `cross_reward_v1_adapter_soft` | `reward_v1_only` | `adapter_scale_soft_v1` | default | Directly test whether the two best Phase 5.2 single-axis signals combine well. |
| `cross_reward_v1_mpc_health` | `reward_v1_only` | default | `mpc_health_v1` | Check whether reward health pressure offsets MPC smoothness side effects. |
| `cross_adapter_soft_mpc_health` | legacy | `adapter_scale_soft_v1` | `mpc_health_v1` | Separate adapter+MPC interaction from reward effects. |
| `cross_reward_v1_adapter_soft_mpc_health` | `reward_v1_only` | `adapter_scale_soft_v1` | `mpc_health_v1` | Very-high-risk full Phase 5.2 combination. It is sentinel-only until pairwise results are reviewed. |

Because `mpc_health_v1_only` caused strong clip/depth regression in Phase 5.2, all MPC-including crosses are lower priority and must pass a short sentinel before 200-iteration candidate training. `cross_reward_v1_adapter_soft` is the first and most important cross because it directly tests the user's hypothesis.

Stage A execution priority is:

```text
1. Run cross_reward_v1_adapter_soft through sentinel and, if healthy, candidate training.
2. Run MPC-containing pairwise crosses as sentinel-only first.
3. Promote an MPC-containing pairwise cross to 200 iterations only after sentinel review.
4. Do not run the full triple cross for 200 iterations until pairwise results have been reviewed.
```

## Future Reward-Tuning Formula

Reward variants are not part of the first Stage A screen. They are reserved for the next parameter-tuning step if the cross-combination screen shows that reward is still the most promising axis. If that happens, the tuning should keep the Phase 5.2 reward shape and change only saturation or fallback-reason terms:

```text
r_5_3 = r_legacy
        - w_fallback(reason) * I[fallback_used]
        - w_pwm_sat * mean(max(0, abs(pwm_i) - pwm_soft_limit) / (1 - pwm_soft_limit))
        - w_latency * min(max(0, latency_ms - latency_ref_ms) / latency_ref_ms, latency_clip)
        - w_action * ||action_4d||_2^2
        - w_delta_action * ||action_4d - previous_action_4d||_2^2
```

Default constants inherited from Phase 5.2 unless a profile overrides them:

```text
pwm_soft_limit = 0.90
latency_ref_ms = 20.0
latency_clip = 3.0
w_fallback = 0.30
w_pwm_sat = 0.20
w_latency = 0.05
w_action = 0.01
w_delta_action = 0.02
```

Possible next-step reward tuning candidates for the next phase or Stage B handoff:

| Profile ID | Changed term | Values | Purpose |
|---|---|---|---|
| `reward_v1_pwm_sat_030` | saturation penalty | `w_fallback=0.30`, `w_pwm_sat=0.30` | Gentle saturation pressure. |
| `reward_v1_pwm_sat_040` | saturation penalty | `w_fallback=0.30`, `w_pwm_sat=0.40` | Stronger saturation pressure. |
| `reward_v1_reason_aware_v0` | fallback reasons and saturation | `w_pwm_sat=0.30`, `timeout=0.20`, `no_cost_improvement=0.35`, `nonfinite/exception=0.50`, default fallback=0.30 | Avoid treating every fallback as equally bad. |

Optional later probe, not part of the first matrix:

```text
reward_v1_delta_smooth_probe:
  w_pwm_sat = 0.30
  w_delta_action = 0.04
```

This optional probe is only allowed if the first matrix still shows action or reference oscillation as the likely saturation source.

## Requirements

1. **Phase 5.2 baseline contract**: Phase 5.3 must treat `reward_v1_only` as the immediate comparison baseline and `baseline_rerun` as the health floor.
   - Current: Phase 5.2 results exist in `docs/phase5_2_server_training_results.md` and `source/results/koopman_phase5_2_server/phase5_2_experiment_summary.json`.
   - Target: Phase 5.3 selectors and reports compare every candidate against both Phase 5.2 `reward_v1_only` and Phase 5.2 `baseline_rerun`.
   - Acceptance: A Phase 5.3 report includes `comparison_baseline=reward_v1_only`, `health_floor=baseline_rerun`, and the source result paths.

2. **Cross-combination screening matrix**: Phase 5.3 must explicitly test combinations of Phase 5.2's reward, adapter and MPC profiles.
   - Current: Phase 5.2 tested only one changed axis at a time.
   - Target: The first matrix includes `cross_reward_v1_adapter_soft`, `cross_reward_v1_mpc_health`, `cross_adapter_soft_mpc_health` and `cross_reward_v1_adapter_soft_mpc_health`.
   - Acceptance: Local tests prove every cross profile resolves to exactly one reward profile, one adapter profile, one MPC profile and a declared risk level.

3. **Sentinel-before-candidate rule**: High-risk combinations must not run full candidate training before a short sentinel.
   - Current: `mpc_health_v1_only` had large clip/depth regression in Phase 5.2.
   - Target: Any cross containing `mpc_health_v1` runs a 50-iteration sentinel and is promoted to 200 iterations only if it does not trigger hard failures or obvious metric blow-up.
   - Acceptance: Training summaries record `screening_stage=sentinel|candidate`, `risk_level`, and the sentinel pass/fail reason.

4. **Training ladder**: Phase 5.3 must not run long training before a short sentinel validates the profile.
   - Current: Phase 5.2 ran 200-iteration candidates after local tests.
   - Target: Each candidate uses a `50` iteration sentinel first, then a `200` iteration candidate if sentinel passes, then at most one optional `400` iteration extended run for the best candidate.
   - Acceptance: Training summaries record `training_ladder_stage`, `max_iterations`, `save_interval`, `profile_id`, and checkpoint provenance.

5. **Promotion gate**: A candidate can only be promoted if it improves the multi-metric health tradeoff.
   - Current: `reward_v1_only` reduced fallback but worsened saturation, clip and depth RMSE.
   - Target: Promotion requires multi-metric health improvement against `reward_v1_only`, not only saturation improvement.
   - Acceptance: The selected manifest exists only if all hard gates pass and the candidate satisfies:

```text
hard safety gates:
  finite logs
  bounded PWM inside [-1, 1]
  valid Phase 5.3 checkpoint provenance
  adapter refresh before env.step
  matched step/sine/irregular logs validate

promotion gates against reward_v1_only:
  pwm_saturation_rate_mean <= reward_v1_only_mean - 0.05
  or relative PWM saturation improvement >= 15 percent

  at least one of:
    policy_action_clip_rate_mean <= reward_v1_only_mean - 0.02
    or relative clip improvement >= 10 percent

    depth_rmse_mean <= reward_v1_only_mean - 0.03
    or relative depth RMSE improvement >= 5 percent

regression guards:
  fallback_rate_mean <= reward_v1_only_mean + 0.02
  attitude_rmse_mean <= reward_v1_only_mean * 1.05
  latency_ms_mean < 20.0

health-floor report:
  candidate must also report whether PWM saturation, fallback, clip, depth RMSE
  and attitude RMSE are better, equal or worse than baseline_rerun.
```

The `baseline_rerun` comparison is not optional. If a candidate improves versus
`reward_v1_only` but remains clearly worse than `baseline_rerun` on PWM
saturation or depth RMSE, the report must label it as `partial_improvement`
rather than final promotion.

6. **Composite health ranking**: Phase 5.3 must rank candidates by a declared multi-metric health score, not by one metric alone.
   - Current: Phase 5.2 selected `reward_v1_only` by qualitative balance after one-factor ablation.
   - Target: Phase 5.3 reports both hard gates and a composite score.
   - Acceptance: Candidate reports include:

```text
health_score =
  0.30 * pwm_saturation_improvement
  + 0.20 * fallback_improvement
  + 0.20 * clip_improvement
  + 0.20 * depth_rmse_improvement
  + 0.10 * attitude_rmse_improvement
```

   where each improvement is measured against Phase 5.2 `reward_v1_only`, clipped to a documented range, and never used to override a hard safety/regression gate.

The normalization contract is:

```text
improvement(metric) =
  clamp((baseline_metric - candidate_metric) / max(abs(baseline_metric), eps), -1.0, 1.0)
```

All ranked metrics are lower-is-better. `health_score` ranks only candidates
that have already passed hard safety gates and promotion/regression guards.

7. **Handoff to parameter tuning**: Phase 5.3 selects a combination family, not a final policy.
   - Current: Phase 5.2 selected `reward_v1_only` as the best balanced single-axis candidate.
   - Target: Phase 5.3 selects the best cross-combination family and recommends the next parameter-tuning axis.
   - Acceptance: The Phase 5.3 report states `selected_combination`, `why_selected`, `next_tuning_axis`, and `parameters_to_sweep_next`.

8. **Matched evaluation remains mandatory**: Any promoted Phase 5.3 candidate must run step, sine and irregular matched evaluation.
   - Current: Phase 5.2 matched eval used 350 samples per trajectory and all logs passed validation.
   - Target: Phase 5.3 uses the same matched eval shape unless the plan records a deliberate reviewed change.
   - Acceptance: `workflows/validate_ppo_koopman_log.py` accepts all selected-candidate logs and the report includes per-trajectory metrics.

9. **Evidence labels and provenance**: Phase 5.3 checkpoints must not be relabeled Phase 5.2 candidates.
   - Current: Phase 5.2 has `phase5_2_health_candidate` and `phase5_2_matched_eval`.
   - Target: Phase 5.3 introduces `phase5_3_cross_sentinel`, `phase5_3_cross_candidate`, `phase5_3_cross_extended`, and `phase5_3_cross_matched_eval`.
   - Acceptance: Provenance validators reject Phase 5.1 or Phase 5.2 summaries when a Phase 5.3 checkpoint is required.

10. **Claim boundary**: Phase 5.3 reports must state exactly what was improved and what remains unproven.
   - Current: Phase 5.2 correctly refused final promotion because saturation regressed.
   - Target: Phase 5.3 may claim multi-metric health refinement only if the gate passes.
   - Acceptance: Summary contains `allowed_claims`, `disallowed_claims`, `remaining_bottlenecks`, and `next_recommended_phase`.

## Boundaries

**In scope:**

- Phase 5.3 SPEC and PLAN for user review.
- Cross-combination profile definitions.
- Sentinel and candidate training for reasonable Phase 5.2 profile combinations.
- Selection of the best parameter-combination family for the next phase.
- Phase 5.3 evidence/provenance labels.
- Local profile, reward, selector and validator tests.
- Server sentinel, candidate and optional extended training.
- Matched step/sine/irregular evaluation.
- Selection report comparing against Phase 5.2 `reward_v1_only` and `baseline_rerun`.

**Out of scope:**

- LLM supervisor or LLM tuning interface - Phase 6.
- Hand-written PPO or replacing RSL-RL PPO - out of architecture scope.
- PPO direct 8D PWM - violates controller boundary.
- Changing PPO observation/action dimensions - invalidates Phase 5 comparison.
- Full factorial or large hyperparameter search - too expensive before combination screening.
- Treating the best Phase 5.3 cross as final - it only selects the next tuning direction.
- MPC solver rewrite - Phase 5.3 is reward refinement first.
- Koopman retraining or `paper_lifted_edmd` promotion - separate model work.
- Multi-env training - requires a vectorized adapter refresh audit first.
- Deployment or legacy-superiority claim - requires broader evaluation.

## Constraints

- Local work must remain Isaac-free except source-contract checks.
- Server training remains on `agentic-AUV` under Isaac Sim 5.0 + Isaac Lab 2.2.1.
- `legacy_easyuuv_v0` remains the default reward unless a CLI/profile explicitly selects a Phase 5.3 variant.
- Every run must record profile metadata and source baseline metadata.
- Every selected candidate must have reloadable checkpoint provenance.
- If no Phase 5.3 profile passes, the correct output is `no_selection`, not a forced promotion.

## Stop Conditions

Stop and discuss before continuing if:

- Any Phase 5.3 reward variant produces NaN or Inf rewards.
- Sentinel training fails before writing a valid summary.
- PWM leaves `[-1, 1]`.
- Mean fallback rises above `0.20` during matched evaluation.
- No cross combination improves the composite health score versus `reward_v1_only`.
- Depth RMSE or attitude RMSE worsens by more than the declared regression guard versus `reward_v1_only`.
- Action clip rate fails to improve and remains above `reward_v1_only`.
- A full factorial or the full triple cross is tempting before pairwise Stage A results are reviewed.
