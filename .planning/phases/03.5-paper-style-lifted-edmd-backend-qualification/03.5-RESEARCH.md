# Phase 3.5 Research Notes

## Research Question

Phase 3.5 is not asking whether Koopman-MPC can run at all. Phase 3 answered that.

Phase 3.5 asks:

```text
Does the paper-style lifted EDMD backend provide a defensible algorithmic comparison
against the direct-state engineering backend for EasyUUV?
```

## Relation To The Two Papers

### EasyUUV Side

EasyUUV contributes the layered control architecture:

```text
high-level policy or generated reference
  -> low-level controller
  -> 8D PWM
  -> thrust allocation / hydrodynamics / Isaac physics
```

The important rule is that Koopman-MPC should sit in the low-level controller layer. PPO or future high-level policies should produce references or corrections, not directly bypass the low-level safety boundary.

Phase 3.5 preserves this:

```text
reference trajectory
  -> paper_lifted_edmd MPC
  -> bounded 8D PWM
  -> existing EasyUUV physics
```

### Koopman-Sim2Real Side

The Koopman-Sim2Real direction contributes:

```text
data collection
  -> EDMD / lifted dynamics
  -> finite-horizon control
  -> robot rollout
  -> deferred optional online adaptation
```

The key paper-aligned distinction is lifted-space evolution:

```text
f[k+1] = f[k] * Theta
```

This differs from direct next-state regression:

```text
x[k+1] = W * [phi(x[k], r[k]), u[k]]
```

Phase 3.5 strengthens the paper connection by treating the lifted-space form as its own backend, not as an incidental candidate hidden inside a sweep.

## Adaptation To EasyUUV

The original paper's physical state/control dimensions cannot be copied directly.

EasyUUV currently uses:

```text
state_dim = 11
reference_dim = 5
control_dim = 8
```

Therefore the valid claim is not exact dimensional reproduction. The valid claim is structural:

```text
observable dictionary -> EDMD transition in lifted space -> MPC rollout
```

The observable dictionary must stay small:

- state;
- attitude/depth tracking error;
- PWM;
- selected velocity/rate squared terms;
- PWM squared terms;
- optional bias.

This follows the Phase 2.5 recommendation to avoid an opaque, high-dimensional polynomial or RBF dictionary before the data supports it.

## What Counts As Evidence

Strong evidence for Phase 3.5:

- held-out multi-step prediction stays finite;
- no divergence at required horizons;
- offline MPC returns bounded PWM with low fallback rate;
- repeated Isaac smoke runs do not crash;
- paper-lifted logs contain solver diagnostics;
- direct-state and paper-lifted reports are side by side.

Weak evidence:

- one-step RMSE only;
- one two-sample smoke only;
- a paper-style model that is trained but never used by MPC;
- a report that hides the fact that direct-state was safer.

## Expected Failure Modes

Paper-style lifted EDMD may fail because:

- the observable dictionary is still too small;
- normalization makes ridge behavior unstable;
- held-out trajectories differ too much from training;
- multi-step rollout drifts even when one-step RMSE looks acceptable;
- the MPC solver finds bounded commands but falls back too often;
- Isaac closed-loop dynamics reveal errors hidden by offline replay.

These are valid results. If they happen, Phase 3.5 should document them and let Phase 4 proceed with direct-state first.

## Reporting Language

Use precise language:

```text
paper-style lifted EDMD backend
paper-aligned comparison backend
lifted-space transition over observables
```

Avoid overclaims:

```text
full paper reproduction
Sim2Real-ready controller
final controller improvement
```

## Phase 4 Impact

If Phase 3.5 passes, Phase 4 becomes:

```text
legacy vs direct_state Koopman-MPC vs paper_lifted_edmd Koopman-MPC
```

If Phase 3.5 fails, Phase 4 becomes:

```text
legacy vs direct_state Koopman-MPC
with paper_lifted_edmd failure analysis included
```

Both outcomes are useful. The difference is whether the paper-style backend is eligible for full closed-loop evaluation.
