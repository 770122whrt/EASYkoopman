# Phase 5.1: Koopman-MPC PPO Stability Training - Specification

## Execution Readiness

Current review status:

```text
PASS_WITH_MUST_FIXES_BEFORE_EXECUTION
```

The Phase 5.1 direction is approved, but the current code still treats Koopman-MPC PPO evidence as Phase 5 smoke evidence. Phase 5.1 must not be executed on the server until the new evidence levels, provenance labels, training-health summary, stability validator and matched-evaluation gate are implemented.

## Goal

Prove that the Koopman-MPC-specific PPO training chain can run stably beyond smoke length before any reward redesign or performance claim.

The phase answers:

```text
Can RSL-RL PPO train through heuristic_reference_delta_v0 and direct_state Koopman+MPC for a meaningful run, produce reloadable checkpoints and complete matched evaluation without numerical or controller-health failure?
```

## Required Claim Boundary

Phase 5.1 may claim:

```text
The PPO-Koopman-MPC chain completed a bounded longer training run.
The produced checkpoint reloads and can be evaluated on matched references.
Training health, fallback, latency, clipping and PWM bounds were recorded.
```

Phase 5.1 must not claim:

```text
The policy is globally optimal.
The policy is deployable.
The policy is superior to legacy/Ssurface unless matched evaluation proves that specific metric.
The reward is final.
The paper_lifted_edmd backend is qualified as the default controller.
```

## Algorithm Contract

Phase 5.1 does not invent a new PPO algorithm. It trains a Koopman-MPC-conditioned PPO policy checkpoint: a set of RSL-RL PPO weights produced inside the `PPO -> adapter -> Koopman+MPC` closed-loop training path, with provenance proving where those weights came from.

The control contract remains:

```text
obs_9d
  -> RSL-RL PPO policy
  -> action_4d
  -> heuristic_reference_delta_v0
  -> koopman_reference_5d
  -> refresh env._koopman_reference_5d
  -> env.step(action_4d)
  -> direct_state Koopman+MPC
  -> pwm_8d
  -> EasyUUV physics
```

Do not reinterpret this as:

```text
PPO -> Koopman latent state
PPO -> 8D PWM
PPO replaces MPC
Koopman replaces PPO observation
```

Any Phase 5.1 implementation must preserve:

- PPO observation dimension: 9.
- PPO action dimension: 4.
- PWM dimension: 8.
- Adapter mode: `heuristic_reference_delta_v0`.
- Koopman backend: `direct_state`.
- Checkpoint provenance: explicit Phase 5.1 provenance labels, not relabeled Phase 5 smoke provenance.

## Stability Evidence Levels

Phase 5.1 introduces evidence levels that are stronger than Phase 5 smoke but still below final performance proof:

```text
retrained_policy_smoke:
  one-iteration or tiny evaluation evidence from Phase 5

stability_sentinel:
  short training beyond smoke, used to validate logging, checkpointing and no immediate instability

stability_candidate:
  longer single-env training run that is eligible for matched evaluation

matched_stability_eval:
  checkpoint has completed matched step/sine/irregular evaluation
```

Do not introduce a stronger label such as `converged_policy` in this phase.

## Run Ladder

The first server ladder should be:

```text
1. sentinel run:
   num_envs = 1
   max_iterations = 50
   save_interval = 10
   reward_profile = legacy_easyuuv_v0

2. stability run:
   num_envs = 1
   max_iterations = 200
   save_interval = 25
   reward_profile = legacy_easyuuv_v0

3. matched evaluation:
   evaluate selected checkpoints on step, sine and irregular references
```

These numbers are intentionally modest. They are long enough to expose stability problems, but bounded enough for the Isaac server workflow.

## Initial Pass Thresholds

Hard failures:

- Training crashes or hangs.
- No checkpoint is produced.
- Checkpoint cannot be loaded.
- Any non-finite observation, action, PWM or reward is detected.
- PWM exceeds the actuator bound.
- Adapter refresh does not occur on the step path.
- Evaluation cannot complete even the step reference.

Warning thresholds:

- `policy_action_clip_rate > 0.5`.
- `training_loop_fallback_rate > 0.2`.
- `training_loop_latency_ms_mean > 20.0`.
- `training_loop_latency_ms_max > 50.0`.
- `latency_budget_violation_rate > 0.1`.
- Matched evaluation finishes but tracking error is worse than controller-only Koopman+MPC on all trajectories.

Warnings do not automatically fail the phase. They route the next improvement.

The `20 ms` mean-latency threshold is a training warning, not a real-time deployability claim. Real-time control budget must be recorded separately through `control_loop_budget_ms` and `latency_budget_violation_rate`.

## Reward Boundary

The first stability proof uses:

```text
reward_profile = legacy_easyuuv_v0
```

Reason: the chain has only smoke evidence. Changing reward before proving longer training stability would make attribution unclear.

After the stability run passes, Phase 5.1 may prepare but does not have to execute a versioned reward profile:

```text
reward_profile = koopman_mpc_stability_v1
```

The first bounded reward redesign may include:

- Tracking error term.
- Action magnitude penalty.
- Action delta penalty.
- PWM saturation penalty.
- Koopman-MPC fallback penalty.
- Solver latency soft penalty.

It must not include an LLM term or direct PWM imitation term.

## Matched Evaluation Contract

Matched evaluation must compare at least:

```text
legacy/Ssurface
direct_state Koopman+MPC controller-only
PPO -> heuristic_reference_delta_v0 -> direct_state Koopman+MPC
```

The same reference set must be used:

```text
step
sine
irregular
```

For this phase, matched evaluation is used to diagnose stability and failure modes. It may report metric differences, but the main success criterion remains training stability.

Matched evaluation must be driven by `selected_ppo_checkpoint_manifest.json`, not by ad hoc checkpoint path selection. The selected checkpoint must pass Phase 5.1 provenance validation before Isaac startup.

## Improvement Routing

After matched evaluation, route the next phase by observed bottleneck:

```text
fallback-dominated:
  inspect MPC feasibility, fallback policy and fallback-aware reward

latency-dominated:
  optimize solver settings, horizon, warm start or control update frequency

action-clipping-dominated:
  tune adapter scales or add action regularization

tracking-error-dominated:
  tune reward weights or reference curriculum

unstable-training:
  shorten curriculum, lower learning rate or improve reset/reference distribution

clean-stable-but-weak:
  proceed to reward/profile ablation
```

## In Scope

- Phase 5.1 planning docs and runbook.
- Longer PPO training on the existing Koopman-MPC path.
- Stability summaries and validators.
- Checkpoint reload and provenance checks.
- Matched evaluation commands and summary aggregation.
- Bounded reward design notes for the next iteration after the stability gate.

## Out Of Scope

- Hand-written PPO.
- PPO direct 8D PWM.
- LLM control or online LLM tuning.
- Sim2Real or hardware claims.
- Switching to `paper_lifted_edmd` as default.
- Multi-env training unless a specific vectorized adapter gate is added.
- Claiming final performance superiority from one long run.

## Stop Conditions

Stop and discuss before expanding the scope if:

- The stability run cannot complete because solver latency dominates runtime.
- Fallback rate is consistently above 0.5.
- Checkpoint reload fails after training succeeds.
- Reward signals are missing or non-finite.
- The current wrapper cannot be safely extended to the required run duration.
- Performance pressure tempts the project to skip matched evaluation.
