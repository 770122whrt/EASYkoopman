# Phase 2.5 Summary: Offline Koopman Model Qualification Gate

**Date:** 2026-07-01
**Branch:** `isaaclab2-migration`
**Status:** local implementation complete; server log gate still pending
**Primary follow-up:** package this branch to the Isaac server and run the Phase 2.5 gate on real step/sine/irregular logs.

## 1. 本阶段的目的

Phase 2.5 的目的不是“再训练一个 Koopman 模型”，而是在 Phase 3 接入 Koopman+MPC 前建立一个正式的模型准入 gate。

换句话说，本阶段只回答一个问题：

```text
这个 Koopman 模型是否足够稳定、可泛化、可复现，并且比简单 baseline 更有价值？
```

如果答案是 `pass`，Phase 3 可以把 `selected_model_manifest.json` 当作 MPC 预测模型入口。
如果答案是 `fail`，Phase 3 不应该继续接这个模型；这通常说明数据覆盖不足、模型发散、泛化失败，或者模型甚至没有超过简单 baseline。

这个 gate 很重要，因为 MPC 会把模型预测结果放进闭环优化里。如果模型只是在训练日志上误差很低，但在 held-out 轨迹上发散，那么进入闭环后控制器可能会持续追逐错误预测，最终导致仿真不稳定。

## 2. 和前后阶段的关系

Phase 1 负责从 Isaac / EasyUUV legacy controller 中采集数据。它输出 Koopman JSONL，每一行包含：

```text
t
state
reference
action_4d
pwm_8d
next_state
trajectory_type
controller_mode
```

Phase 2 负责把这些 JSONL 日志转成离线矩阵，并实现最基本的 direct-state EDMD 训练链路：

```text
JSONL -> X/U/R/Y/t -> lifting -> ridge EDMD -> model.json -> metrics.json
```

Phase 2.5 在 Phase 2 的基础上加了一层“质量判断”：

```text
validated JSONL logs
-> log-level train/validation/test split
-> direct-state Koopman candidate
-> paper-style lifted EDMD candidate
-> persistence/simple-linear baselines
-> validation/test multi-step rollout
-> selected_model_manifest.json
-> gate_report.md
```

Phase 3 才会开始真正替换控制器，做 Koopman+MPC。Phase 3 不应该自己猜模型路径、维度、dt 或 normalization 行为，而应该读取 Phase 2.5 输出的 `selected_model_manifest.json`。

## 3. 数据变量和维度

当前日志被整理成以下矩阵：

```text
X: 当前状态矩阵，shape = (N, 11)
U: 8D PWM 控制输入，shape = (N, 8)
R: 参考目标，shape = (N, 5)
Y: 下一时刻状态矩阵，shape = (N, 11)
t: 时间戳，shape = (N,)
```

对应单步符号：

```text
x_k     = state[k]       in R^11
u_k     = pwm_8d[k]      in R^8
r_k     = reference[k]   in R^5
x_{k+1} = next_state[k]  in R^11
```

这里训练控制输入使用 `pwm_8d`，而不是 `action_4d`。原因是 `action_4d` 是 legacy controller 的中间指令，`pwm_8d` 更接近实际进入推进器映射前的控制量，所以更适合作为 Koopman 模型的输入。

## 4. Direct-State Koopman Candidate

Direct-state candidate 是 Phase 2 已经实现的工程 baseline。它的形式是：

```text
phi_k = lift(x_k, r_k)
z_k   = [phi_k, u_k]
x_hat_{k+1} = W z_k
```

训练时使用 ridge regression：

```text
W* = argmin_W || Z W^T - Y ||_2^2 + lambda || W ||_2^2
```

其中：

```text
Z = [z_1; z_2; ...; z_N]
Y = [x_2; x_3; ...; x_{N+1}]
lambda = ridge regularization coefficient
```

这个模型的优点是简单、直接、容易调试，也能作为后续 MPC 的工程起点。它的局限是：它直接预测 raw state，不完全等价于 Koopman-Sim2Real 文章里更典型的 lifted observable evolution。

相关文件：

- `koopman/lifting.py`: direct-state 使用的 `lift_state_reference()` 和 `LiftingConfig`。
- `koopman/edmd.py`: `fit_edmd()`，训练 direct-state candidate。
- `koopman/model.py`: `KoopmanModel`，负责保存、加载和 `predict_next()`。

## 5. Paper-Style Lifted EDMD Candidate

Phase 2.5 新增了更接近论文形式的 lifted-space EDMD candidate。它不直接拟合 `x_{k+1}`，而是拟合 observable vector 的线性演化：

```text
f_k = psi(x_k, r_k, u_k)
f_hat_{k+1} = Theta^T f_k
x_hat_{k+1} = state_slice(f_hat_{k+1})
```

当前 `psi()` 至少包含：

```text
x_k
x_k[:5] - r_k
u_k
selected velocity/rate squared terms
u_k squared
bias
```

也就是说，raw state 是 lifted observable 的一部分。预测时先得到下一步 observable，再从 observable 的 state slice 中取回 `x_hat_{k+1}`。

对应训练目标：

```text
Theta* = argmin_Theta || F Theta - F_next ||_2^2 + lambda || Theta ||_2^2
```

其中：

```text
F      = [f_1; f_2; ...; f_N]
F_next = [psi(x_2, r_1, u_1); psi(x_3, r_2, u_2); ...]
```

注意：这里 `F_next` 当前仍使用日志中的 `next_state` 与同一步的 `reference/pwm` 构造，这是一个离线工程近似。它已经比 direct-state 更接近 lifted evolution，但 Phase 3 做 MPC 时仍需要根据控制预测 horizon 进一步定义未来 reference/control 的使用方式。

相关文件：

- `koopman/observables.py`: `PaperObservableConfig` 和 `build_observables()`。
- `koopman/lifted_edmd.py`: `LiftedEDMDModel` 和 `fit_lifted_edmd()`。

## 6. Baselines 的意义

Phase 2.5 加了两个 baseline：

### Persistence Baseline

```text
x_hat_{k+1} = x_k
```

这个 baseline 的含义是“假设下一步状态不变”。如果 Koopman 模型连这个都打不过，说明它没有学到有用动力学。

### Simple Linear Baseline

```text
z_k = [1, x_k, u_k, r_k]
x_hat_{k+1} = W z_k
```

这个 baseline 是不做 Koopman lifting 的普通线性回归。如果 Koopman 模型不优于它，那么复杂 lifting 暂时没有带来收益。

相关文件：

- `koopman/baselines.py`: `PersistenceBaseline`、`SimpleLinearBaseline`、`fit_simple_linear_baseline()`。

Gate 规则是：最终 selected model 必须优于 persistence 和 simple linear baseline，否则 `gate_status = fail`。

## 7. 为什么必须使用 Log-Level Split

本阶段禁止 row-level random split。原因是仿真轨迹是时间序列，相邻样本高度相关。如果把同一条连续轨迹随机拆成训练集和验证集，验证误差会被严重低估。

正确做法是按日志文件拆分：

```text
train_logs      = 若干完整 JSONL
validation_logs = 若干完整 JSONL
test_logs       = 若干完整 JSONL
```

最小推荐组合：

```text
train:      koopman_step_long.jsonl
validation: koopman_sine_long.jsonl
test:       koopman_irregular_long.jsonl
```

更好的组合是多次运行、多种初始条件、多种目标轨迹，把多个日志放进 train，再用不同轨迹类型做 validation/test。

相关文件：

- `koopman/splits.py`: `SplitManifest`、`create_explicit_split()`、`validate_split_manifest()`。
- `workflows/split_koopman_logs.py`: 生成 split manifest 的 CLI。

## 8. Sweep 在做什么

Sweep 会系统比较多个模型组合，而不是手动挑一个看起来不错的参数。

默认搜索空间：

```text
model_class:
  - direct_state
  - paper_lifted_edmd

ridge:
  - 1e-8
  - 1e-6
  - 1e-4
  - 1e-2

lifting_variant:
  - linear
  - selected_quadratic

normalization:
  - off
  - standard
```

每个 candidate 都会：

1. 在 train logs 上训练。
2. 在 validation logs 上评估。
3. 保存 model artifact。
4. 保存 metrics artifact。
5. 写入 `sweep_results.json`。

排序优先级：

```text
1. 未发散优先
2. validation multi_step_rmse@20 更低优先
3. validation multi_step_rmse@60 更低优先
4. 指标接近时，更简单的 lifting 优先
```

相关文件：

- `koopman/sweep.py`: `run_sweep()`。
- `workflows/sweep_koopman_models.py`: sweep CLI。

## 9. Divergence-Aware Evaluation

Phase 2 只有 one-step RMSE 和单个 multi-step RMSE。Phase 2.5 增加了更适合 MPC 前检查的指标：

```text
one_step_rmse
depth_rmse
velocity_rmse
attitude_angle_rmse
multi_step_rmse@5
multi_step_rmse@20
multi_step_rmse@60
max_error
nonfinite_count
divergence_rate@5
divergence_rate@20
divergence_rate@60
diverged
```

核心思想是：MPC 不是只看一步预测，它会使用多步 horizon。因此模型必须在多步 rollout 中稳定。

当前 divergence 判定包括：

```text
prediction 出现 NaN/Inf
depth 超出 physical envelope
attitude 超出 physical envelope
velocity/rate 超出 physical envelope
divergence_rate@20 > 0
在 horizon 足够时 multi_step_rmse@60 > 3 * one_step_rmse
```

相关文件：

- `koopman/evaluation.py`: `evaluate_model()`、`rollout_predictions()`、`has_diverged()`。

## 10. Selection 和 Gate Report

Selection 会从 `sweep_results.json` 中挑出当前最好的 candidate，然后做准入判断。

准入条件：

```text
candidate validation 不发散
candidate 优于 persistence baseline
candidate 优于 simple linear baseline
candidate held-out test 不发散
```

如果满足条件，输出：

```json
{
  "gate_status": "pass",
  "model_class": "...",
  "model_path": "...",
  "normalizer_path": "...",
  "metrics": {...},
  "baselines": {...}
}
```

如果不满足条件，也会输出 manifest，但状态是：

```json
{
  "gate_status": "fail",
  "known_limitations": [
    "selected candidate did not beat persistence and simple linear baselines"
  ]
}
```

这不是异常，而是 gate 正常工作。它阻止我们把不可靠模型接进闭环控制。

相关文件：

- `koopman/selection.py`: `select_model_from_sweep()`。
- `koopman/gate_report.py`: `write_gate_report()`。
- `workflows/select_koopman_model.py`: 生成 `selected_model_manifest.json`。
- `workflows/write_koopman_gate_report.py`: 生成 `gate_report.md`。

## 11. 服务器使用流程

完整服务器流程见：

```text
docs/phase2_5_koopman_gate_runbook.md
```

核心命令顺序如下。

### 1. 验证日志

```bash
cd "$EASYKOOPMAN_DIR"

python workflows/validate_koopman_log.py source/results/koopman_phase1/koopman_step_long.jsonl
python workflows/validate_koopman_log.py source/results/koopman_phase1/koopman_sine_long.jsonl
python workflows/validate_koopman_log.py source/results/koopman_phase1/koopman_irregular_long.jsonl
```

### 2. 创建 split

```bash
python workflows/split_koopman_logs.py \
  --train-log source/results/koopman_phase1/koopman_step_long.jsonl \
  --validation-log source/results/koopman_phase1/koopman_sine_long.jsonl \
  --test-log source/results/koopman_phase1/koopman_irregular_long.jsonl \
  --output source/results/koopman_phase2_5/split_manifest.json \
  --seed 7 \
  --notes "phase2.5 first gate"
```

### 3. 跑 sweep

```bash
python workflows/sweep_koopman_models.py \
  --split-manifest source/results/koopman_phase2_5/split_manifest.json \
  --output-dir source/results/koopman_phase2_5/sweep
```

### 4. 选择模型

```bash
python workflows/select_koopman_model.py \
  --sweep-results source/results/koopman_phase2_5/sweep/sweep_results.json \
  --output source/results/koopman_phase2_5/selected_model_manifest.json
```

### 5. 写报告

```bash
python workflows/write_koopman_gate_report.py \
  --manifest source/results/koopman_phase2_5/selected_model_manifest.json \
  --sweep-results source/results/koopman_phase2_5/sweep/sweep_results.json \
  --output source/results/koopman_phase2_5/gate_report.md
```

## 14. 当前限制和后续注意点

1. 本阶段不实现 MPC。MPC 是 Phase 3。
2. 本阶段不在 Isaac 中闭环运行 Koopman controller。
3. 当前 sine / irregular 日志采集仍依赖 legacy eval workflow 和可用 checkpoint；如果服务器报错，需要单独 debug 采集脚本。
4. 如果日志数量不足，正确结果是 data-insufficient 或 gate fail，而不是强行 row-level split。
5. 如果 selected model 没有超过 baseline，说明当前 Koopman 设计暂时没有足够收益，应先补数据或调整 observable。
6. 如果 validation/test 多步 rollout 发散，应优先扩大轨迹覆盖、检查状态尺度和 normalization，再考虑进入 MPC。

## 15. Phase 3 的进入条件

只有同时满足以下条件，才进入 Phase 3：

```text
selected_model_manifest.json exists
gate_report.md exists
gate_status == pass
selected model beats persistence baseline
selected model beats simple linear baseline
validation rollout does not diverge
held-out test rollout does not diverge
```

Phase 3 应读取 `selected_model_manifest.json`，而不是手写模型路径或默认参数。
