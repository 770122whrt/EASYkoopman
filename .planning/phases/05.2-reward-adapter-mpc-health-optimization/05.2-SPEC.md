# Phase 5.2: Reward, Adapter, and MPC Health Optimization - Specification

## Goal

Create a bounded Phase 5.2 tuning loop that tests whether reward shaping, adapter scale calibration, and MPC health parameters can reduce the Phase 5.1 bottlenecks without breaking the proven PPO -> adapter -> Koopman+MPC training chain.

The phase answers:

```text
Can a versioned, evidence-labeled tuning profile reduce fallback, PWM saturation, or action clipping relative to the Phase 5.1 candidate while preserving reloadable checkpoint evidence and matched step/sine/irregular evaluation?
```

## Phase 5.1 Input Evidence

Phase 5.1 produced the first reliable candidate checkpoint:

```text
/root/IsaacLab/logs/rsl_rl/easyuuv_koopman_mpc/2026-07-05_00-28-00/model_199.pt
```

Matched evaluation passed schema gates, but exposed health bottlenecks:

| Trajectory | Fallback rate | Fallback reasons | PWM saturation rate | Action clip mean | Depth RMSE |
|---|---:|---|---:|---:|---:|
| step | 0.1343 | no_cost_improvement=22, timeout=25 | 0.2757 | 0.0786 | 0.7057 |
| sine | 0.0314 | no_cost_improvement=9, timeout=2 | 0.4664 | 0.2364 | 0.5350 |
| irregular | 0.0971 | no_cost_improvement=27, timeout=7 | 0.3746 | 0.1236 | 0.5737 |

This points to three concrete tuning targets:

```text
fallback health:
  no_cost_improvement and timeout both occur

PWM health:
  saturation rate is high even when fallback is modest

policy/adapter health:
  action clipping is visible, especially on sine
```

## Required Claim Boundary

Phase 5.2 may claim:

```text
A specific versioned tuning profile improved a measured health metric versus the Phase 5.1 candidate under matched evaluation.
The tuned checkpoint is reloadable and preserves the PPO 9D -> 4D action contract.
The run stayed inside actuator bounds and reported fallback, latency, saturation, clipping and tracking metrics.
```

Phase 5.2 must not claim:

```text
Final PPO convergence.
Deployment readiness.
Broad superiority over legacy/Ssurface.
Reward finality.
Generalization beyond the tested references.
Paper-lifted EDMD default-controller qualification.
```

## Algorithm Contract

The control chain remains unchanged:

```text
obs_9d
  -> RSL-RL PPO policy
  -> action_4d
  -> heuristic_reference_delta_v0
  -> koopman_reference_5d
  -> direct_state Koopman+MPC
  -> pwm_8d
  -> Isaac EasyUUV physics
```

Phase 5.2 may tune only versioned metadata around this chain:

```text
reward_profile:
  legacy_easyuuv_v0 or koopman_mpc_stability_v1

adapter_profile:
  heuristic_reference_delta_v0_default, adapter_scale_soft_v1, or reserved adapter_scale_soft_v2

mpc_profile:
  mpc_default_v0, mpc_health_v1, or reserved mpc_delta_limit_probe_v1

profile_id:
  unique run label combining the above choices
```

It must not replace RSL-RL PPO, change the policy observation/action dimensions, or allow PPO to send direct PWM.

## Requirements

1. **Phase 5.1 health baseline ingestion**: Phase 5.2 must consume the Phase 5.1 selected manifest and matched logs as the baseline.
   - Current: `matched_eval_summary.json` exists, but the fallback reasons and saturation metrics were computed manually.
   - Target: A local Isaac-free analysis workflow reads Phase 5.1 JSONL logs and writes a reproducible health baseline.
   - Acceptance: Running the analyzer on `source/results/koopman_phase5_1/ppo_{step,sine,irregular}.jsonl` reports fallback rate, fallback reason counts, PWM saturation rate, action clipping and depth RMSE for each trajectory.

2. **Versioned reward profile**: Phase 5.2 must introduce a non-default reward profile named `koopman_mpc_stability_v1`.
   - Current: `reward_profile=legacy_easyuuv_v0` is passed through training, but EasyUUV rewards remain the legacy tracking/action shape.
   - Target: `koopman_mpc_stability_v1` adds bounded health penalties for fallback, PWM saturation, latency, action magnitude and action delta while preserving the PPO 9D/4D contract.
   - Acceptance: Source-contract tests prove `legacy_easyuuv_v0` remains unchanged and `koopman_mpc_stability_v1` contains explicit health terms with versioned scale fields.

3. **Reward formula contract**: The first reward profile must be simple enough to audit and attribute.
   - Current: There is no explicit formula for Koopman-MPC-aware PPO reward.
   - Target: The profile uses:

```text
r_v1 = r_legacy
       - w_fallback(reason) * I[fallback_used]
       - w_pwm_sat * mean(max(0, abs(pwm_i) - pwm_soft_limit) / (1 - pwm_soft_limit))
       - w_latency * min(max(0, latency_ms - latency_ref_ms) / latency_ref_ms, latency_clip)
       - w_action * ||action_4d||_2^2
       - w_delta_action * ||action_4d - previous_action_4d||_2^2
```

   - Acceptance: Tests or a pure helper function verify the formula returns finite values, zero health penalty for healthy controller diagnostics, thresholded latency behavior, and larger penalty when fallback or PWM saturation is present.

4. **One-factor ablation profiles**: Phase 5.2 must evaluate each tuning axis separately before any combined profile.
   - Current: Phase 5.1 used one profile only: legacy reward, default adapter scales and default MPC settings.
   - Target: The first server matrix contains at least baseline re-run, reward-only, adapter-only and MPC-only candidates.
   - Acceptance: Every training summary contains `profile_id`, `reward_profile`, `adapter_profile`, `mpc_profile`, `changed_axis` and `source_baseline_manifest`.

5. **Profile provenance and evidence labels**: Phase 5.2 checkpoints must not be confused with Phase 5.1 candidates.
   - Current: Phase 5.1 provenance labels stop Phase 5 smoke relabeling, but no Phase 5.2 labels exist.
   - Target: Phase 5.2 introduces explicit labels:

```text
phase5_2_health_sentinel
phase5_2_health_candidate
phase5_2_matched_eval
```

   - Acceptance: Validators reject a Phase 5.1 `stability_candidate` summary if it is presented as a Phase 5.2 tuned candidate.

6. **Health selection gate**: A tuned candidate is selected only if it improves at least one primary health metric without introducing hard failures.
   - Current: Phase 5.1 selected a stable candidate but not a health-improved candidate.
   - Target: Selection requires finite logs, bounded PWM, valid checkpoint provenance and a documented improvement against the Phase 5.1 baseline.
   - Acceptance: A selected Phase 5.2 manifest states `selected_reason`, `improved_metric`, `baseline_value`, `candidate_value`, `regression_checks` and `allowed_claims`.

7. **Matched evaluation remains mandatory**: Every candidate that claims improvement must run matched step/sine/irregular evaluation.
   - Current: Phase 5.1 matched eval passed with 350 samples per trajectory.
   - Target: Phase 5.2 matched eval uses the same trajectories and comparable `steps_per_action`/`trajectory_cycles`.
   - Acceptance: `validate_ppo_koopman_log.py` accepts all selected-candidate logs and the Phase 5.2 report compares against Phase 5.1 using identical metric names.

8. **Reviewer approval gate**: The first implementation must not start server training until the user approves the Phase 5.2 profile values.
   - Current: Candidate parameter values are not yet locked.
   - Target: The review checklist in this spec is explicitly accepted or revised before code execution.
   - Acceptance: The Phase 5.2 summary records the approved profile values and whether any were changed during review.

## Initial Candidate Values

These values incorporate the Phase 5.2 review document. They are the first implementation defaults unless later evidence forces a revision.

### Reward Profile: `koopman_mpc_stability_v1`

```text
pwm_soft_limit = 0.90
latency_ref_ms = 20.0
latency_clip = 3.0
w_fallback = 0.30
w_pwm_sat = 0.20
w_latency = 0.05 thresholded above latency_ref_ms
w_action = 0.01
w_delta_action = 0.02
```

Optional reason-aware fallback penalty, if implemented instead of a single scalar:

```text
nonfinite_input / exception: 0.50
no_cost_improvement: 0.30
timeout: 0.15
```

Rationale:

```text
fallback penalty should be visible but not dominate the roughly 0.65 ordinary shaped reward scale.
PWM saturation penalty targets high saturation without forbidding strong thrust.
latency penalty is thresholded because Phase 5.1 latency mean was healthy.
action penalties are deliberately small because the low-level controller remains MPC.
```

Required reward diagnostics:

```text
r_legacy
fallback_penalty
pwm_saturation_penalty
latency_penalty
action_penalty
delta_action_penalty
r_total
```

### Adapter Profile: `adapter_scale_soft_v1`

```text
policy_action_limit = 1.0
rpy_delta_scale = 0.30
depth_delta_scale = 0.40
depth_bounds = [-3.0, 3.0]
```

Reserved stronger backup profile, not part of the first matrix:

```text
adapter_scale_soft_v2:
  policy_action_limit = 1.0
  rpy_delta_scale = 0.25
  depth_delta_scale = 0.30
  depth_bounds = [-3.0, 3.0]
```

Rationale:

```text
Keep the action domain unchanged, but reduce the reference delta generated per action more gently than the first draft.
This tests reference aggressiveness, not raw action clipping alone.
```

Required adapter diagnostics:

```text
reference_delta_norm_mean
reference_delta_norm_max
depth_reference_delta_mean
attitude_reference_delta_mean
depth_rmse
attitude_rmse
```

### MPC Profile: `mpc_health_v1`

```text
mpc_horizon = 5
mpc_timeout_ms = 12.0
mpc_delta_pwm_limit = 0.35
mpc_depth_weight = 1.0
mpc_attitude_weight = 1.0
mpc_control_weight = 0.03
mpc_smoothness_weight = 0.10
```

Reserved delta-limit probe, not part of first `mpc_health_v1_only`:

```text
mpc_delta_limit_probe_v1:
  mpc_delta_pwm_limit = 0.25
  mpc_control_weight = 0.03
  mpc_smoothness_weight = 0.10
  mpc_horizon = 5
  mpc_timeout_ms = 12.0
```

Rationale:

```text
Increase control and smoothness penalties to reduce saturation and sudden PWM changes.
Keep delta PWM limit unchanged in the first MPC health profile so no_cost_improvement fallback attribution stays clean.
Lower delta PWM limit only in a separate probe after weights-only results are reviewed.
```

## Boundaries

**In scope:**

- Reproducible Phase 5.1 health analysis.
- Versioned `koopman_mpc_stability_v1` reward profile.
- Versioned adapter and MPC profile metadata.
- One-factor server ablation: baseline, reward-only, adapter-only, MPC-only.
- Optional `mpc_delta_limit_probe_v1` only after weights-only MPC results are reviewed.
- Phase 5.2 checkpoint provenance, selected manifest and matched evaluation report.
- Local tests and validators that are Isaac-free where possible.

**Out of scope:**

- Hand-written PPO - RSL-RL remains the PPO implementation.
- PPO direct 8D PWM - violates the architecture.
- Changing PPO observation/action dimensions - would invalidate Phase 5.1 comparison.
- Multi-env training - remains blocked until vectorized adapter refresh is tested separately.
- Paper-lifted EDMD default controller - still research/comparison only.
- LLM tuning - remains Phase 6 and must not enter real-time control.
- Final performance ranking against legacy - requires broader evaluation after a tuned candidate exists.
- Sim2Real or hardware readiness - deferred.

## Constraints

- Local-first implementation. Isaac is required only for training and matched rollout.
- Every candidate run must carry a `profile_id`.
- Only one tuning axis changes per ablation candidate.
- A combined profile is not part of the initial Phase 5.2 matrix. It may only become Phase 5.2b or Phase 5.3 after single-axis results and user approval.
- Failure must be classified, not hidden: fallback-dominated, saturation-dominated, clip-dominated, latency-dominated, tracking-regression or unstable-training.
- `legacy_easyuuv_v0` must remain the default unless the CLI explicitly asks for `koopman_mpc_stability_v1`.
- `baseline_rerun` is mandatory and must use the same server, code commit, Koopman manifest, seed when available, training length, matched evaluation settings and analyzer version as candidate runs.

## Stop Conditions

Stop and discuss before continuing if:

- Reward v1 causes NaN/Inf rewards or observation/action instability.
- Any candidate has fallback rate above `0.50` on step evaluation.
- PWM exceeds actuator bounds.
- The adapter-only profile improves clipping but causes a large tracking regression.
- The MPC-only profile reduces saturation but increases fallback due to `no_cost_improvement`.
- `mpc_delta_limit_probe_v1` increases no_cost_improvement fallback over the weights-only MPC profile.
- Combined profile is tempting before single-axis results are available and reviewed.

## Review Incorporation Summary

The Phase 5.2 review document changed the first implementation contract:

1. `w_fallback` changes from `0.50` to `0.30`, unless reason-aware fallback penalties are implemented.
2. `adapter_scale_soft_v1` changes from `0.25 / 0.30` to `0.30 / 0.40`; the stronger values become `adapter_scale_soft_v2`.
3. `mpc_health_v1` keeps `mpc_delta_pwm_limit = 0.35`; `0.25` becomes `mpc_delta_limit_probe_v1`.
4. `baseline_rerun` is mandatory.
5. Candidate selection uses relative and absolute improvement plus fallback, depth RMSE and attitude RMSE regression guards.
6. Combined profile is excluded from the initial Phase 5.2 matrix.

## Candidate Promotion Rule

Candidate promotion requires all hard gates plus both relative and absolute evidence:

```text
primary health metric mean across trajectories improves by at least 20 percent
and primary health metric absolute improvement reaches the minimum visible change
```

Minimum visible changes:

```text
pwm_saturation_rate: >= 0.05 absolute
fallback_rate: >= 0.015 absolute if baseline >= 0.05
policy_action_clip_rate_mean: >= 0.03 absolute
```

Regression guards:

```text
fallback_rate:
  no trajectory may have both absolute increase > 0.02 and relative increase > 25%

depth_rmse:
  mean depth RMSE may not worsen by more than 10%

attitude_rmse / quaternion_error:
  mean attitude RMSE may not worsen by more than 10%

matched evaluation:
  step, sine and irregular must complete for promotion; partial runs are diagnostic only
```
